# Recorded CCD body order in the staged performance fixture

The direct Kotlin and Java compatibility CCD routes now agree in all 11 recorded state and event channels over 120 measured steps. Both use staged local Maven artifacts and an explicit body hash. This is a bounded fixture diagnosis. The [performance manifest task](https://github.com/rubixhacker/dyn4k/issues/17) and performance qualification remain open.

## Prospective fixture choice

Each CCD fixture assigns a zero-based creation index to each body and returns that index from `hashCode()`. The two static walls receive indices 0 and 1. The 25 small-scene bullet circles receive indices 2 through 26. The counter belongs to one fixture, so warm-up construction does not shift the measured world's hashes. Both routes use the same scheme. Non-CCD families still construct ordinary bodies. No world or engine ordering code changed.

The approved [version 1 manifest](performance-manifest-v1.json) fixes 999 scenario IDs, 21 targets, 28 runtime rows, geometry, materials, motion, event cadence, solver settings, and budgets. It did not prescribe Java object identity hashes. The creation-index hash is a prospective CCD fixture-order rule. It changes hash-table traversal and can change collision solver order; therefore the old ordinary-identity CCD samples are **superseded observations**, not samples of this rule. The manifest's physical inputs and approved performance policy remain intact. The [new raw trace index](performance-ccd-order-v1/result.json) records the exact hash rule and workload IDs. Its three hashed identity CSVs verify the initial body hashes, positions, and bullet flags against the pinned baseline. The staged test repeats that check and compares direct/compatibility state and event rows.

The [CCD fixture revision](performance-ccd-fixture-v2.json) now gives this prospective rule its own version and SHA-256. It links the unchanged version 1 manifest hash and lists all 27 affected CCD workload IDs. The [version 4 fixture record](performance-candidate-v4/fixture-revision.json) binds that revision to the committed Java and Kotlin fixture source hashes and the three raw identity traces. The separate [final review correction](performance-final-review-fix.md) records the archive checks added after independent review.

The separate frozen [hash-order probe](/tmp/dyn4k-ccd-order-probe/result.md) compared four hash offsets and full body-state/order traces on baseline and a mixed Kotlin diagnostic JAR. Matching offsets produced byte-identical 120-step traces; changing the offset changed solver order and state. The separate frozen [actual-route probe](/tmp/dyn4k-ccd-route-probe/result.md) first reproduced the ordinary-identity route difference at step 27. Changing only the two body creation sites in each fixture made the two candidate routes match for 120 steps. With its temporary Vector2/simplex repair JAR, baseline and both routes matched all 11 recorded simulation channels. Those probes are controls, not measurements of the final staged consumer. Their report JSON SHA-256 values are `17cfcf056fd41122adda169561cebb3c70329456bfd3c696f31da03ec1d3bac7` and `93d6bd3e34da104cb3dd675d87154df1e6fd6436d7f478329c2fa44f1a709e77`, respectively. The original, stable-hash, and mixed-diagnostic actual-route CSVs have byte-preserving copies under [probe controls](performance-ccd-order-v1/probe-controls/).
