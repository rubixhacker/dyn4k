# Numerical tolerance calibration evidence

Research for [Establish numerical tolerance calibration evidence](https://github.com/rubixhacker/dyn4k/issues/12), observed 2026-09-13. This answers evidence gathering, not approval of limits or execution of the acceptance suite.

## Evidence boundary

The inspected shallow checkout of dyn4j tag `6.0.0` resolves to `058bf6d982a0fb89b54050f929f6ea9dae53b714`, matching the [baseline report](baseline.md). All upstream links below pin that revision. Investigation used source inspection and targeted searches of production and test sources; no simulation, cross-target probe, test suite, or numerical measurement was run. Numbers quoted below are **upstream inputs/assertion deltas**, never proposed or approved dyn4k tolerances. This is a representative calibration inventory, not the exhaustive baseline-test accounting required by migration acceptance.

The baseline's default step is `1/60` second. Solver inputs include six velocity iterations, two position iterations, a `0.005` linear tolerance and a two-degree angular tolerance. These are algorithm parameters, **not comparison allowances**. Explicit fixture overrides must be retained. [Settings source](https://github.com/dyn4j/dyn4j/blob/058bf6d982a0fb89b54050f929f6ea9dae53b714/src/main/java/org/dyn4j/dynamics/Settings.java#L38-L103). `step(n)` repeats the configured fixed timestep; `step(n, dt)` uses the supplied timestep for each step. [World implementation](https://github.com/dyn4j/dyn4j/blob/058bf6d982a0fb89b54050f929f6ea9dae53b714/src/main/java/org/dyn4j/world/AbstractPhysicsWorld.java#L310-L337).

## What the observed numbers mean

The inventory spans exact checks, inequalities and explicit deltas of different magnitudes. Rounded expected literals such as the CCD time `0.577` lose information about the actual baseline result: their assertion delta cannot establish baseline-to-port error. Solver slop, expected-value rounding, physical approximation and backend floating-point differences are distinct error sources. Therefore neither a global `1e-3` allowance nor automatic reuse of every upstream delta is justified by this evidence.

Required migration accounting still preserves original test meaning. A proposed stronger differential fixture supplements a rounded upstream assertion; it must not silently replace or weaken it. Numerically close outputs that change detection, contact order, wake state or another discrete outcome require investigation under the approved two-layer policy.

## Proposed calibration protocol, not ratified criteria

1. Build a fixture manifest from the complete baseline suite. For each selected scenario record source method, coordinate/quantity units, characteristic scale, body/shape/material inputs, order of construction, full settings, fixed timestep schedule, duration and checkpoints. Identify mode coverage and missing cases separately from numeric limits.
2. Run the pinned baseline JVM artifact to capture full-precision reference trajectories and discrete event traces. Record artifact/source hashes, fixture revision, JVM/OS/architecture and run command. Repeat controlled baseline runs to expose nondeterminism before interpreting port differences. Reference retention/update governance remains a human decision.
3. Check analytically tractable cases independently and vary timestep, scale and threshold-adjacent inputs in separate diagnostic probes. This reveals conditioning and baseline discretization behavior; the comparison fixture itself keeps its specified inputs fixed. Do not make a baseline bug into an unapproved correction.
4. Propose per-quantity absolute/relative limits with evidence and margin rationale. Apply the approved scalar formula `abs(actual-baseline) <= absoluteLimit + relativeLimit*abs(baseline)`. Specify vector metric, angular wrapping policy and invariant metric explicitly. Check every checkpoint independently, and reject unexpected non-finite values. An angle's wrapped orientation and accumulated rotations may require different metrics.
5. Seek explicit approval before those limits become acceptance criteria. Missing evidence remains a gate. A failing implementation cannot widen limits automatically; changing a limit requires fresh evidence and human review.
6. Once an engine exists, execute identical fixtures through Kotlin and shim surfaces on every approved target/runtime/build lane. Retain observed errors and discrete traces tied to the exact candidate. Diagnose differences before any approved exceptional policy change. Neither JVM baseline repeats nor successful compilation proves these lanes.

## What can be settled now and what cannot

Before implementation, researchers can inventory assertions, generate baseline references, establish fixture reproducibility, identify physical invariants and propose justified initial limits. Baseline-only runs cannot measure dyn4k error, compiler/backend drift, shared-state solver integration, optimized versus debug behavior, or cross-target reproducibility. This report has performed the inventory step only; reference generation and empirical calibration remain outstanding.

Remaining human choices include the concrete supported scales/horizons, selected metric per quantity, per-fixture numerical limits after measurements, reference retention/update rules and any baseline-bug exception. None is ratified by closing this research ticket. The existing all-target contract and requirement for nonempty contact-solver evidence remain intact.
