# Portable numerical consumer

The standalone consumer in `tools/numerical/portable` runs common Kotlin engine calls through staged `dyn4k-core` Maven publications. Its Gradle build does not include project source modules or the Java recorder. Run it from a clean commit. The runner freshly builds and hashes the metadata, JVM, Android, Linux x64, JS, Wasm JS, and Wasm WASI publications before any host task executes.

```sh
ANDROID_HOME="$HOME/Android/Sdk" python3 tools/numerical/portable/run.py \
  --prospective-baseline /var/tmp/dyn4k-portable-baseline-evidence \
  --output /var/tmp/dyn4k-portable-numerical-evidence
```

The runner executes JVM on Java 21 and Java 8, Android host, Linux x64, Node JS, Node Wasm JS, and Node Wasm WASI test tasks. The Java 8 lane selects the Gradle test launcher from `/tmp/dyn4k-tools/jdk8`; its receipt hashes the process Gradle actually launched. The Linux x64 lane retains `execve` traces and requires the actual executed `.kexe` to match the linked binary and its SHA-256. Android host execution uses a JVM. It does not qualify an Android device. The publication log and manifest bind the staged artifacts to the clean source revision. The runner executes the 15 matrix test methods separately so Gradle can finish each large raw JUnit report, then assembles one ordered JSONL trace and case inventory. Each completed lane retains a Gradle log and raw XML for every method, the whole trace, per-case traces, SHA-256 receipt, and result. The receipt requires all 15 current XML reports and checks every method's target process. Every lane without execution gets a `NOT_RUN` or `UNAVAILABLE` receipt with zero executed cases and an unpassed qualification status.

## Recorded contract

The declaration in `cases.py` is the expected case set. The suite records every inner step, ordered step, contact, and time-of-impact callbacks, before-step actions, and configured outer endpoint copies. Endpoint copies do not advance the step or event history. Each state records body transforms, prior transforms, velocity, force, torque, rest state, energy, momentum, joint reactions, and fixed-origin position. Geometry cases also record direct SAT and GJK observations. Nonfinite values appear as tagged raw values; receipt inspection rejects them outside the known Angle physical failure. Floating-point comparison uses binary64 bits, including the sign of zero, before any tolerance decision.

The six families are geometry/collision boundaries across scales and offsets; free motion, forces, damping, and restitution; default and separately configured contact, friction, sleep, and wake; all ten joint types with initial and active modes, false/true/timed toggles for 34 applicable boolean controls, 86 numeric value cases, and 12 equal or range limit cases; circle and pentagon CCD at 30, 60, and 120 Hz; and a 600-second free-motion invariant scene. A separate 600-step Angle ratio `-1` case retains the reproduced baseline nonfinite failure while allowing other test methods to run. Default sleep/wake uses its own 30/60/120 Hz step. Configured sleep/wake uses 120 Hz inner steps and separate 4/2/1 outer endpoint groups. Its six cases include both repetitions at each outer rate.

The receipt validator rejects missing or duplicate cases, missing steps, lost callbacks, altered action steps, reordered events, changed input, changed signed zero, missing endpoints, stale artifacts, and an empty suite. It retains tagged nonfinite values only in states of the known Angle ratio `-1` case and records that physical failure. The receipt binds the exact Git archive hash, commit, staged metadata and target artifact hashes, runtime identity, trace hash, and expected and executed counts.
Each host result also enumerates reference coverage. The frozen catalog maps 14 of 332 declared cases to pinned traces. The other 318 are listed as `UNPASSED_REFERENCE_COVERAGE` for that catalog. A separately verified pinned baseline capture supplies prospective references for those 318 cases; their numerical policies remain unpassed until recorded. Executing or sealing a case does not count as numerical parity.

`baseline_capture.py` builds the same Kotlin fixture and recorder sources in a separate JVM reference project against the fixed dyn4j 6.0.0 JAR. It verifies the JAR SHA-256 before copying it into an evidence directory, runs each of the 15 fixture methods, retains raw XML, logs, whole and per-case traces, and records the actual JVM executable, source archive, portable fixture-source, and baseline JAR hashes. Its inventory rejects missing or duplicate cases, missing steps and methods, and nonfinite values outside the known Angle ratio `-1` case. Verify a completed archive with `baseline_capture.py --verify-existing --output <capture-dir>`. That pass checks method and case bytes against the whole trace and writes `verified.json`; the host runner requires this file for prospective comparison. The Angle case first overflows recorded kinetic energy at step 87 and reaches nonfinite angular velocity at step 171. It remains a failed physical case. The earlier baseline-only Java probe recorded angular velocity but not kinetic energy. The 14 previously frozen traces remain separate and unchanged.

For each of the 318 prospective cases, `prospective_compare.py` requires the verified pinned JAR and fixture-source identities, the sealed candidate trace, exact case input, complete every-step coverage, record and event order, and the baseline case hash. It rejects altered input, changed signed zero, structural changes, missing records, and nonfinite output. It reports finite numerical differences without applying an unapproved tolerance. Bit-exact matches are labeled `EXACT_DIAGNOSTIC`; a finite difference is `UNPASSED_NUMERICAL_POLICY`. Both retain `qualification: UNPASSED` until the fixture policy is recorded and executed on each target. A missing capture is `UNAVAILABLE_REFERENCE`, not a case pass.

The Pulley preparation is a continuation: its second segment records absolute steps 2 and 3 after the first segment's step 1. The receipt checks that starting step and rejects a reset or gap. Frozen projections are required on each mapped input, step, callback, action, and configured endpoint. The receipt also checks the fixed frozen case ID, origin, scale and configured grouping against the declared case, so a changed projected identity cannot pass while the portable input stays unchanged.

`reference_diagnostic.py` first checks the frozen gzip and input hashes and attempts a streamed comparison of the raw portable records, including an explicit signed-zero check. It reports the raw transport schema differences. It then compares the complete typed frozen projection with the approved comparator, and separately records overlapping body channels and exact-value differences. The projected comparison fails on missing or reordered records, signed zero, unapproved channels, or failed approved limits.

For the 14 frozen case mappings, the common recorder also captures typed projections of the complete frozen input header, baseline settings, world configuration, the initial body/fixture/joint state, every later body/joint state, ordered StepListener, collision, contact and TOI payloads, actions, instrumented callbacks, and configured outer endpoints. It reads engine values from the staged publication and rejects an unexpected algorithm, shape, filter, or joint type. The diagnostic streams the complete projected sequence through the approved comparator, including signed zero, and separately reports exact event and auxiliary-record differences. On the pre-integration Android host run, all 14 input projections had the frozen structure; value differences remained in the old `pow` TOI epsilon, World broadphase tracking and one Weld perimeter ratio, and Pulley main initial state. The nominal Java 8 run projected all 108,001 StepListener records exactly. A focused JVM run projected all 1,801 Weld and all eight first Pulley preparation events exactly; the second preparation and Pulley main still differed numerically. The pre-integration configured 120 Hz run recorded 935,991 projected events against 935,967 frozen events, with 467,938 exact events; the 24 surplus callbacks and later value differences remain failed. These projections are embedded in the portable trace and reproducible from its source revision. Any projected mismatch or channel without an approved rule remains unpassed; the raw envelope's additional recorder fields are reported separately.

The nominal force, torque, accumulated force and accumulated torque fields are positive zero in all 36,000 frozen samples and in the corresponding Java 8 projection: 432,000 exact-zero values across both traces. The nominal fixture now contains the approved exact-zero rules for these four channels. The diagnostic checks positive zero on both sides, rejects nonzero and negative-zero controls, and fails the projected verdict if this rule fails. It applies no new tolerance. Final integrated candidate execution remains pending.

The [delegated nominal timestep decision](https://github.com/rubixhacker/dyn4k/issues/7#issuecomment-6243538631) now requires five exact finite binary64 getter values on every `StepListener` callback in the fixed 60 Hz fixture. The portable comparator applies those five exact paths in memory without changing the frozen catalog. A separate stream audit checks both the pinned reference and portable projection against the required values, requires 108,001 callbacks and the single `updatePerformed` callback, and rejects a changed or nonfinite getter. The pinned baseline capture passed 540,005 getter comparisons. That baseline control does not qualify the final integrated candidate or another target runtime.

The pinned nominal scene replaces both broadphase trees before adding its body. The portable fixture now makes those same common Kotlin engine calls, so the three tracking flags in its frozen input header match the pinned Java scene. The pinned Weld scene first adds a circular fixture to a body already in the world, then replaces it with a rectangle; the portable fixture follows that sequence to retain the same initial CCD tree state. Focused runs against the pinned dyn4j JAR confirmed exact frozen input headers for both corrected cases. These setup checks do not establish parity for their later steps or callbacks.

The configured 120 Hz JVM wake sample also projected its before-wake state, impulse action, and after-wake state as three exact auxiliary records against the pinned reference. Its other old-source event differences remain failed.

The physical diagnostic reuses the approved represented-geometry depth and phase schedule for default and configured sleep/wake cases. It reports all nine case counts and failed steps separately; default failures remain failures. The 36,000-step free-motion invariant is checked against its analytic limits. These diagnostics do not replace input, event, or complete-channel parity.

The runner also applies the approved six-group same-run exact checks to all three default and six configured contact cases. The checks enforce the fixed floor, zero applied and accumulated force, sleeping velocities and pose relative to that run's previous sleeping state, the immediate center impulse, transform aliases and phase-correct previous copies with ten getter duplicates, and timestep metadata. Configured outer endpoints must be exact copies immediately after their inner state and never advance the temporal chain. The checker requires actual sleeping and repeated sleeping states, the full before/action/after sequence, every inner state, and the expected timestep and endpoint counts. Its `exact-consistency.json` is a separate verdict; a same-run pass does not repair a frozen parity or physical failure. The semantics follow pinned `docs/research/sleep-wake-exact-checks.mjs` and `docs/research/sleep-wake-quality-exact-checks.mjs` at `44dd7cf05502fa4b5fdc3523e3271c3cba335de8`.

The runner invokes that diagnostic for every frozen reference found in `--reference-dir`, using `/tmp/dyn4k-configured-control/baseline-trace` by default. Each host gets `frozen-comparison.json` with explicit unavailable references. A missing reference, nonmatching schema, or failed approved channel never becomes a parity pass.
Independent frozen case comparisons run in four bounded worker processes after each host test. The result list remains in fixture order, and each worker reads only the retained per-case trace and its pinned reference.

## Acceptance boundary

The pinned baseline is dyn4j 6.0.0 at source revision `058bf6d982a0fb89b54050f929f6ea9dae53b714` and binary SHA-256 `204ca8dd55626ad3727b82dacb37df1800c5eff0d6bb6e782b6e5af5162b2b3e`. The approved 14 reference traces use the frozen Java schema and exact input headers. The portable recorder keeps additional receipt fields around a typed frozen projection. A successful portable receipt proves that its declared cases ran and were bound to staged artifacts; numerical parity requires the complete projected comparison to pass every approved rule, and physical qualification remains separate. Any unmatched projected input, event, state, case, or runtime remains unpassed.

The configured control in `/tmp/dyn4k-configured-control/result.md` is a mixed diagnostic. Its 1,025,970 matching runtime records do not qualify one coherent candidate artifact. The previous `pow` versus pinned `cbrt` default TOI input difference must be checked on the final merged source. The Angle ratio `-1` case produced `-Infinity` at step 171 with the pinned baseline alone, as recorded in `/tmp/dyn4k-angle-baseline-probe/result.json`. It remains a failed physical case and is ineligible as a finite numerical reference. Neither observation permits a trace rewrite or a wider acceptance limit.
