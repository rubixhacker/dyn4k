# Full staged Chromium consumer

This consumer executes the approved 2,523 portable Kotlin test methods against separately staged `dyn4k-core-js` and `dyn4k-js` KLIBs. It covers four `js:Chromium` staged consumer configurations. It does not qualify numerical parity, physical correctness, performance, or the complete 112-lane release matrix.

The project in `consumers/qualification/portable/full-browser/` has its own Gradle root and two test modules. It reads the original core and facade test sources from the exact candidate checkout. It resolves both published modules from an external Maven directory. The original JS platform `actual` sources are included for core. Each test compile and executable link uses the resolved published friend KLIB.

`tools/qualification/full_browser_consumer.py run` requires an exact clean checkout, the candidate commit, staged KLIB hashes selected outside the producer, and one pinned Chromium binary. It requires JDK 21, Gradle 9.5.0, KGP 2.4.20, and cached dependencies. Set `JAVA_HOME=/tmp/dyn4k-tools/jdk21`, `GRADLE_USER_HOME` to the existing cached home, and `TMPDIR` to a home-backed evidence directory. Put `--output` and the staging repository outside the source checkout. The command uses Gradle `--offline --rerun-tasks` and writes every build and raw result under the output's home-backed parent.

The consumer has its own committed Yarn lock, generated by offline resolution from the cached toolchain. The producer checks its Git blob and seeds the temporary Kotlin JS store with those bytes. The archive retains source and method input TSVs, provider graphs, and staged KLIB copies. It also retains original Gradle output, browser XML, raw Karma messages, and Karma configuration. Each module retains reporter and browser process attestations, the linked test JS, and selected source bytes captured by Karma's Node reporter. The reporter writes large diagnostic messages in smaller lines so Gradle can process the complete test event stream. The raw message remains in the archive. The verifier checks its SHA-256. The producer records the raw method order and requires 2,465 core plus 58 facade methods with no failure or skip. A source compile or a smaller suite is `NOT_RUN` for this gate.

`verify` requires the caller to supply the candidate, lane, browser path, both staged KLIB hashes, and an independently calculated archive digest. It checks the complete archive inventory and bytes before reading results. It compares test sources and every approved method to Git blobs and the immutable manifest. It then replays raw Karma and XML method identities, XML order, provider graph, process commands, browser observations, and reporter identity. It validates the entire archived Karma configuration, including selected paths, generated webpack settings, embedded reporter, and port. New captures record the plugin-expanded file list and preprocessor map. The 2e archives predate that runtime record. Their replay validates the complete archived config but cannot retroactively attest the plugin-expanded paths. Replay checks selected source bytes captured by Karma's Node reporter during the browser-start callback against the linked bundle and process interval. The archive does not contain the browser-loaded response body. Replay rejects missing, nonfinite, or negative XML durations. It does not execute a transported bundle. A public verifier rejects a changed archive digest before it considers any future executable replay.

Run `python3 tools/qualification/full_browser_consumer.py --help` for arguments. For example, after a producer finishes, calculate the digest independently with `independent_gates.archive_digest` from a separate checkout, then pass that value to `verify --archive-sha256`. Keep failed attempts in separate evidence directories. The producer does not relabel a failed or partial run as passed.
