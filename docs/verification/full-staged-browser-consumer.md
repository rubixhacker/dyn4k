# Full staged browser consumer

The external project covers 24 approved browser configurations. Each runs 2,523 original portable Kotlin methods against separately staged core and facade KLIBs.

The routes are `js` and `wasmJs`, each on Chromium, Firefox, or Safari. Each family has minimum and current roles in development and production modes. Four older JS Chromium receipts remain replayable only for their exact historical candidate.

The project has its own Gradle root and two test modules. It reads original core and facade test sources from the exact candidate checkout. The core module includes the selected JS or Wasm JS platform test sources. Both modules resolve target KLIBs through Maven GAVs. Their test compiles and executable links use the resolved friend KLIBs.

`tools/qualification/full_browser_consumer.py run` requires a clean exact checkout, external staging repository, and independently selected hashes for both target KLIBs. Chromium 119 and 155 and Firefox 120 and 158 have pinned executable hashes. Safari requires a matching macOS host, an executable in a Safari app bundle, and `--browser-sha256` selected independently. The minimum Safari role requires version 18.2. The current role requires major version 26 or newer. The Safari launcher requests a fresh instance through LaunchServices and waits for it to exit. It observes the new selected process with macOS `libproc`.

Use JDK 21, Gradle 9.5.0, and KGP 2.4.20 with cached dependencies. On Linux, set `JAVA_HOME=/tmp/dyn4k-tools/jdk21`. On macOS, select the task-owned JDK 21 whose executable matches the pinned Darwin hash. Set `GRADLE_USER_HOME` to the task cache and `TMPDIR` to a short, home backed directory. Put output and staging outside the checkout. Resolve pinned dependencies into that cache before capture when needed. The producer uses Gradle `--offline --rerun-tasks` and writes raw output under the selected home directory.

The project pins separate JS and Wasm Yarn locks from offline resolution. The producer captures live lock bytes after the provider graph and each module task. Each capture records the process, time, file identity, and a raw lock copy. A mismatch rejects the route. Public replay checks all three copies against the committed lock and their source process intervals. Earlier receipts without these captures remain historical.

The source inventory binds every original test file to a Git blob. The method contract binds 2,465 core and 58 facade methods to the immutable manifest. The archive retains both resolved KLIBs, provider graphs, Gradle output, raw Karma messages, XML results, and method order. Any missing, duplicate, foreign, failing, or skipped method rejects the route. A source compile or smaller consumer is `NOT_RUN`.

The archived Karma config selects the exact JS script or Wasm JS loader for the mode. The reporter verifies all seven effective Karma patterns, their served and included flags, preprocessors, and pinned implementation inputs. It checks original `isBinary` values before Karma normalization. It also records the selected source bytes in Node during Karma's browser start callback. The record binds the capture to the source process interval and the observed browser identity.

For Wasm JS, the reporter also captures all six generated Kotlin package assets at browser start. It checks their bytes again at completion. The verifier compares the archived Wasm and module files with the linked products and captured package copies.

The task installs a Karma middleware before its file server. It records bytes passed to selected HTTP responses. The archive retains each body and an ordered record of its URL, status, length, hash, browser ID, and process time. Karma preprocesses selected sources through webpack. Both targets require HTTP bodies for the generated runtime and common bundle. The archive also retains both generated entry scripts. Any served entry script must match its archived bytes. Wasm JS requires the emitted, hashed `.wasm` response, which must equal the selected package binary. Karma bundles the loader and JavaScript imports into the common bundle. Those package files remain archived as source inputs; they are not claimed as separate HTTP responses. The source map remains archived as a package asset; browsers need not request it.

The producer rejects missing, duplicate, partial, compressed, or changed selected responses. Public replay compares every body with an archived generated source or package copy. It checks response order and the original process interval. Karma can serve scripts before the reporter's browser-start callback. The original selected source remains separately bound to the linked product. A response record proves bytes passed into Karma's selected server responses; server `finish` does not establish receipt by a browser.

Current-source Safari routes require a separate browser response-body witness. Public replay rejects a missing witness, a changed browser body, a changed process or observer source, a wrong candidate, and a missing Wasm response. It joins each browser record to a Karma response by exact URL, body size, and SHA-256. Browser request order is checked independently of Karma response order because requests can overlap. Earlier Safari schema-3 archives remain replayable only for their exact historical candidate; they establish server output and method execution, not browser-side body bytes.

Safari 27 provides a local `safaridriver --mcp` interface with network request tools, but its `get_network_request` tool describes bodies only for text responses within a size cap. The supplied Mac reports that remote automation is disabled, and `safaridriver --enable` requires an interactive password. The current Safari source checks this condition before building and keeps failed preflight logs. No current Safari route has produced the required browser witness. The new replay shape is a rejection gate, not a claim that the selected Safari process supplied any body bytes. A page-context fetch would be a second request and must be described and correlated as such; it cannot prove the bytes of the original evaluated script.

For Chromium, a separate launcher starts the selected executable at `about:blank` with a private DevTools port. It records its live source-file hash, confirms the DevTools `SystemInfo` browser PID equals the launched and attested Chromium PID, and checks the port's listening socket inode in that process's `/proc` file descriptors. It arms CDP Network before navigating to Karma's capture URL. For each selected generated JavaScript and Wasm response, it retains the original CDP request, response, and finish event parameters and a SHA-256 of `Network.getResponseBody` bytes. The archive retains these bounded browser observations separately from Karma's raw server body files. Public replay requires one browser response for each selected server response, joined by exact Karma URL, with the same body size and hash, exact candidate and module, process PID, launcher source, and process interval. Each observer's request order must be internally consistent; parallel requests can arrive at Karma in a different order from CDP. Replay rejects cached or service-worker responses. This proves the selected Chromium process observed those HTTP response bodies through DevTools; the browser test and raw Karma/XML rows separately establish method execution. It does not prove packet-level delivery, JavaScript evaluation from a particular response, or another browser family. Firefox and Safari retain only the server-side HTTP evidence until an equivalent independent browser observer exists.

The Chromium DevTools client rejects outstanding commands when its socket closes or errors. Connection and command waits each have a 15-second deadline. DevTools HTTP discovery also has a 15-second deadline across retries. Each request and its JSON body read use the remaining time, and the request is aborted when that time expires. A lost connection, missing reply, or silent discovery response fails the capture instead of leaving the producer waiting indefinitely. Historical archives remain bound to their exact original candidate source.

In production mode, the test task copies optimized Wasm products into Karma's package before browser launch. Replay checks those package bytes against the linked optimized Wasm and module files.

`verify` requires the exact candidate, lane, browser executable, both staged KLIB hashes, and an independently calculated archive digest. Safari replay also requires its independently selected executable hash. Replay checks the complete archive inventory before any executable consideration. It verifies source and method hashes, task and mode, raw rows, provider graphs, config bytes, selected assets, HTTP bodies, and process identity. It rejects a changed digest, symlink, wrong runtime, changed bundle, or execution outside the process interval.

Replay accepts a metadata-preserving copy at a new canonical archive path. The receipt keeps the original capture path for process commands and selected-bundle observations. The verifier reads archived bytes at the supplied path. It rejects symbolic paths, hardlinked files, and aliases to the original directory.

The coordinator supplies reviewed source to the approved local Mac and serializes Safari execution. No Safari runtime result is inferred from Linux or a Gradle dry run.

Run `python3 tools/qualification/full_browser_consumer.py --help` for command arguments. Keep failed attempts in distinct evidence directories. An unavailable Safari host remains `UNAVAILABLE` and its browser method gate remains `NOT_RUN`. A passing consumer receipt does not qualify numerical parity, physical behavior, performance, memory, publication, or the 112 lane release matrix.
