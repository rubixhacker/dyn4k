# Sustained performance raw archive

The [performance manifest task](https://github.com/rubixhacker/dyn4k/issues/17) remains open. The [version 1 manifest](../research/performance-manifest-v1.json) fixes the approved budgets and method. The public sustained verifier currently returns `qualification: unpassed`. The approved policy has no numeric admissible-noise or sustained-stress ceiling. It also has no approved harness and adapter binary inventory. These decisions must be added to the frozen policy before production capture or verification. No reference row is qualified now. The historical `verify_candidate_archive.py` still audits the version 1 pilot and returns `unpassed`.

## Commands and archive boundary

Run one capture part on each validated reference host. Keep the trusted HMAC key outside every archive. The key must contain at least 32 bytes and must come from the independent gate operator. The same key verifies every part and the merged archive.

```sh
python3 tools/performance/sustained_archive.py plan
python3 tools/performance/sustained_archive.py init --archive HOST_PART --config REFERENCE_CONFIG.json --trusted-key TRUSTED_KEY
python3 tools/performance/sustained_archive.py capture --archive HOST_PART --job JOB.json --trusted-key TRUSTED_KEY
python3 tools/performance/sustained_archive.py merge --archive COMPLETE_ARCHIVE --part HOST_PART_1 --part HOST_PART_2 --trusted-key TRUSTED_KEY
python3 tools/performance/sustained_archive.py verify --archive COMPLETE_ARCHIVE --trusted-key TRUSTED_KEY --expected-source-commit EXACT_CANDIDATE_SHA
```

Repeat `--part` for all 28 runtime rows after the pending policy decisions. `init` accepts one row and copies staged artifacts, the baseline JAR, runtime, harness, adapter, and probe samples. `capture` appends one signed process record. Failed and partial process files remain in the part and make verification fail. `merge` checks signed parts, copies raw files, rejects duplicate rows, and applies the complete gate. A failed command exits nonzero and prints `qualification: unpassed` with a reason. The independent qualification adapter can call `verify` with its exact candidate SHA and inspect this JSON result. It must supply the trusted key through its own protected input outside the archive.

The full plan has 999 frozen scenario IDs, 21 targets, and 28 runtime rows. It requires 113,886 small and medium process measurements, 18,981 stress reports, 37,296 unchanged-baseline noise runs, and 12,654 plateaus. These counts describe the complete protocol. They are not executed results. Stress is report only; small and medium retain the manifest's row-specific gate assignment.

## Reference config and job contract

The reference config has `source_commit`, `baseline_path`, `artifacts`, and `references`. `artifacts` maps one runtime row ID to absolute staged `core` and `kotlin` artifact paths. `references` maps the same row ID to a validated environment record. The record must reproduce the row's target, runtime family, minimum policy, size assignment, development build, and optimized build. It must select the row's optimized build. It must include hardware, runtime version, ABI, host identity, support verification, and validated power, thermal, and load-window observations. The `runtime`, `harness`, and `adapter` records each need an absolute path. The runtime also needs a version. The `build_receipt.source_path` identifies a JSON receipt with exact source trees, both artifact hashes, the optimized configuration, target, and `status: built_from_exact_source`. The probe needs `timer_source_path` for 10,000 positive `elapsed_ns` samples and `allocation_source_path` for a controlled allocation row. The payload must be at least 1 MiB, measured allocation must cover it, and collection count must be positive. Memory attribution must be validated for managed, native, and Wasm linear storage.

The pending `sustained_gate` policy section must name each row's approved harness and adapter SHA-256, fixture SHA-256, complete `command_prefix`, and exact `environment`. The fixture hash covers the manifest's `fixture` and `joint_parameters` objects. Prefix tokens expand `{runtime}`, `{harness}`, `{adapter}`, `{baseline}`, `{core}`, and `{kotlin}` to selected absolute paths. The JVM prefix must include `-cp` and all five binary paths. The token array binds JVM flags, classpath, main class, and other settings. The producer passes only approved ambient variables plus its fixed `DYN4K_` output variables. The verifier rejects inserted command flags, environment options, and unapproved binary hashes. Loaded harness, adapter, fixture, and engine hashes must appear in the provider receipt. The section also needs numeric `noise_upper_ratio_max`, `stress_wall_ns_max`, and `stress_rss_bytes_max` values. An independent policy decision must justify and approve those values before measuring candidates. The earlier 180-second and 3 GiB pilot limits do not approve sustained limits.

Each job identifies `kind`, `row_id`, `scenario_id`, `mode`, `repeat`, `sequence`, and an absolute `command` array. Noise jobs also identify `side` as `a` or `b`. Kinds are `measure`, `report`, `noise`, and `plateau`. Timing, allocation, and memory run in separate processes. Each gate measurement and noise run measures 600 paced seconds after 120 to 600 seconds of converged warm-up. Each gate measurement has three fresh process repeats. A stress report measures 60 seconds. A plateau has 100 create/use/dispose cycles after warm-up. The three measurement repeat orders are baseline/direct/compatibility, direct/compatibility/baseline, and compatibility/baseline/direct. Non-JVM measurement rows omit the JVM baseline process while retaining the selected candidate order. Noise uses three balanced unchanged-baseline pairs per row and workload.

The command's trailing arguments are `family variant size hz steps mode warmup_steps` for the baseline. Candidate commands append `api`. The frozen scenario ID fixes every value. `capture` checks the entire command before launch. It records PID, monotonic start and end, observed host, binary hashes, and raw output hashes. It reads the executed image from Linux procfs, macOS libproc, or the Windows process API. The signed receipt binds the observed PID and monotonic time to the capture. Only the Linux probe has been exercised on this host. A wrapper must execute the measured runtime in the recorded process.

The runner writes the existing full step CSV to stdout and the full warm-up CSV to stderr. Its stderr must include the existing construction, RSS, and retained-heap markers and `#fixture_reset_after_warmup=1`. It should include `#process_pid` and `#route_marker` (`1` for direct Kotlin, `2` for compatibility). The producer sets these output paths in the runner environment:

| Variable | Required output |
| --- | --- |
| `DYN4K_PROVIDER_JSON` | Loaded API, process PID, source SHA, runtime SHA, baseline SHA, staged artifact SHA values, and loaded provider SHA values. |
| `DYN4K_CLOCK_CSV` | `step,begin_ns,end_ns` for every measured step, using the same monotonic clock as elapsed time. |
| `DYN4K_WARMUP_CLOCK_CSV` | `warmup_step,begin_ns,end_ns` for every warm-up step, using the same monotonic clock. |
| `DYN4K_CLOCK_ORIGIN_JSON` | Runtime PID, monotonic origin stamp, and capture nonce, written by the same process before sampling. |
| `DYN4K_CLOCK_NONCE` | Fresh producer nonce copied into the origin record. |
| `DYN4K_MEMORY_CSV` | `phase,step,managed_bytes,native_bytes,wasm_linear_bytes,attributed_workload_bytes` for `empty`, `construction`, every warm-up step, and every measured memory step. |
| `DYN4K_RESOURCE_CSV` | Observed heap use, RSS, and allocation samples. These observations do not establish workload attribution. |
| `DYN4K_RUN_JSON` | Same-process sample count, measured wall time, activity count, resource peaks, and completion status. |
| `DYN4K_ALLOCATION_V2_JSONL` | Version 2 same-thread allocation counter pairs for construction, warm-up, measurement, or plateau cycles. |
| `DYN4K_MEMORY_V2_JSONL` | Version 2 heap, RSS, buffer-pool, and retained-collection observations. Workload and native attribution remain null. |
| `DYN4K_PLATEAU_V2_JSONL` | Version 2 ordered 100-cycle heap, RSS, and collection-count observations. Workload attribution remains null. |

The memory total must equal the sum of its three disjoint components. The empty workload reading is zero. The verifier checks the 16 MiB small and 64 MiB medium peak caps across construction, warm-up, and measurement. The process RSS stream remains diagnostic. A plateau writes 100 cycles with post-collection heap, RSS, collection count, managed, native, Wasm, total attributable, and reserved runtime bytes. Each attributable component and unexplained RSS residual must stay within the frozen 5% window drift rule. Reserved runtime bytes are recorded separately and require validated attribution.

The producer records the host monotonic interval from process launch to independent observation of the runtime's origin file. The signed origin receipt binds the runtime stamp, PID, and nonce to that interval and the observed process image. Both public verifiers require every warm-up and measured clock row to have positive duration and nonoverlapping monotonic order. One common feasible clock offset must place every row inside the observed process interval. A relative 600-second span alone does not establish that binding. The wide launch-to-origin bracket is deliberately retained in the receipt; a future host probe may narrow it. A trusted signer and runner remain part of the evidence boundary.

Stress runs write `elapsed_ns,rss_bytes,action` external monitor observations. Linux reads the observed PID's `VmHWM` high-water mark. macOS samples `/bin/ps` for the exact PID during the run, converting its current RSS from 1024-byte units as specified by [Apple's `ps(1)` source](https://github.com/apple-oss-distributions/adv_cmds/blob/6bed8737a34dbb54782a18f47dccf933a9967a12/ps/ps.1). Those samples can trigger an early stop but cannot establish a strict peak. For acceptance, the producer calls `wait4` for that exact child PID and records its terminal `ru_maxrss` as bytes, following the [pinned XNU getrusage manual](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/man/man2/getrusage.2). [Apple's wait4 manual](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/wait4.2.html) documents the per-PID terminal resource result. An older [Apple archived getrusage manual](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/getrusage.2.html) instead says kilobytes. Until a hosted probe confirms the reference Mac's API units, that row remains unvalidated. The verifier rejects a terminal value lower than any sampled RSS, so a kilobyte reading cannot be accepted as a smaller byte peak when the sample exposes the mismatch. The terminal value is the final monitor row and the RSS value checked against the row's `stress_rss_bytes_max` policy. A missing terminal result leaves the row unpassed. `wait4` usage may include the child process's children, making this a conservative ceiling check if the runner spawns children. Windows uses `OpenProcess` and `GetProcessMemoryInfo`. It reads the process's lifetime [`PeakWorkingSetSize` in bytes](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters).

The signed monitor receipt binds the PID, method, process image, sample count, peak, exit code, and termination reason. It also records the image observation time and process interval. The Darwin receipt additionally binds the `peak_rss_bytes` metric kind, waited PID, zero wait status, and terminal `ru_maxrss` in bytes. The verifier rejects a sampled-only Darwin receipt, mismatched terminal value, nonzero terminal status, or any RSS high-water above the approved ceiling. Capture terminates when a sampled live RSS value or wall time exceeds an approved ceiling; a transient Mac spike can escape an early stop but remains a failure at terminal verification. Only a completed, zero-exit report within both ceilings is accepted. Stress latency has no absolute pass threshold. Local controls use fake Mac and Windows API responses. A hosted Mac `wait4` capture and Windows native probe remain required before their reference rows can be validated. The policy still has no approved stress ceiling. [XNU's `ri_lifetime_max_phys_footprint`](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/sys/resource.h) measures physical footprint; this route does not substitute that metric for RSS.

The provider JSON cannot attest the process image. The independent OS receipt supplies that digest. The provider's `loaded_core_sha256` must equal the pinned dyn4j JAR for baseline work or the staged core artifact for a candidate run. `loaded_kotlin_sha256` must equal the staged Kotlin artifact only for direct Kotlin. It is `null` on baseline and compatibility runs. `loaded_harness_sha256`, `loaded_adapter_sha256`, and `loaded_fixture_sha256` must match their approved policy values. The producer passes expected source, artifact, and baseline hashes in `DYN4K_SOURCE_COMMIT`, `DYN4K_ARTIFACT_HASHES_JSON`, and `DYN4K_BASELINE_SHA256`. The runner must report what actually loaded.

## Bounded JVM producer audit

The available host can run a short diagnostic against exact staged JVM artifacts. It executes baseline, direct Kotlin, and compatibility routes. It seals source trees, staged classpath bytes, commands, process-image receipts, and raw output with an external key. Its public verifier checks the raw streams and always returns `qualification: unpassed`.

```sh
python3 tools/performance/candidate_runner.py prepare /tmp/dyn4k-tools/jdk21/bin/java HEAD
python3 tools/performance/bounded_adapter.py capture --archive build/performance-bounded --trusted-key /path/outside/archive/operator.key --expected-source-commit EXACT_SOURCE_SHA --java /tmp/dyn4k-tools/jdk21/bin/java --javac /tmp/dyn4k-tools/jdk21/bin/javac --baseline /path/to/pinned/dyn4j-6.0.0.jar --seconds 1 --warmup-seconds 1
python3 tools/performance/bounded_adapter.py verify --archive build/performance-bounded --trusted-key /path/outside/archive/operator.key --expected-source-commit EXACT_SOURCE_SHA
```

Build and stage the exact source before `prepare`. The bounded route allows one to five seconds of warm-up and measurement. It records the three real JVM processes, OS image receipts, full step CSVs, warm-up CSVs, commands, and staged inputs. It reports missing sustained sidecars per route. The historical Java harness and direct Kotlin pilot do not emit in-process clock streams or fixture-reset markers. No available runner emits the full same-process provider and attributed memory records required by the sustained verifier. The bounded audit does not infer them from process RSS or command lines. Its successful exit means the retained bounded raw archive passed its diagnostic checks; it does not mean performance qualified.

## Versioned available-host JVM harness

`tools/performance/sustained_jvm/` contains separate Java and Kotlin adapters. They leave the historical `BaselinePilot.java` and its failed first pilot untouched. The adapters accept the manifest's family, variant, size, rate, step count, mode, and warm-up count. The Java baseline accepts the seven-argument production command; candidate calls append their API. They emit measured and warm-up clock streams, an explicit fixture-reset marker, a same-process provider receipt with SHA-256 of each loaded JAR origin, observed resource rows, and a run summary. The producer separately reads the executed OS process image and binds its digest to the PID and monotonic observation time. The loaded-JAR receipt corroborates JVM state; it is not an independent OS image receipt.

The public host producer builds exact-source staged JVM artifacts, compiles the separate harness, compiles the Kotlin adapter with `direct.init.gradle`, and executes all three API routes. It snapshots source, classpath, runtime, build receipt, commands, clock-origin receipts, and raw streams into a signed archive. Its verifier reads archived binary bytes after relocation, checks the external trusted key, recomputes input hashes, validates every clock row against one process-bound origin offset, checks resource agreement and run activity, and rejects re-signed changes. Use a home-backed `TMPDIR` and keep the key outside the archive:

```sh
TMPDIR="$HOME/dyn4k-performance-tmp" python3 tools/performance/sustained_host.py capture --archive "$HOME/dyn4k-sustained-host-audit" --trusted-key "$HOME/dyn4k-operator.key" --expected-source-commit EXACT_SOURCE_SHA --java /path/to/jdk21/bin/java --javac /path/to/jdk21/bin/javac --baseline /path/to/pinned/dyn4j-6.0.0.jar --seconds 1 --warmup-seconds 1
python3 tools/performance/sustained_host.py verify --archive "$HOME/dyn4k-sustained-host-audit" --trusted-key "$HOME/dyn4k-operator.key" --expected-source-commit EXACT_SOURCE_SHA
```

This host audit accepts only one to five seconds and labels its development build and memory attribution as unqualified. It is an integration proof for real processes and sidecars, not a 600-second calibration. Production `sustained_archive.py capture` passes the resource and run output paths to the same adapters and retains these streams when present. It still requires approved optimized build receipts, validated reference and probe records, attributed memory and plateau evidence, complete workload repeats, admissible noise, and stress ceilings. A short host archive is never accepted by the full gate.

The version 2 short archive accepts `--modes allocation,memory,plateau` and an optional `--producer-root` pointing to an isolated checkout at `--expected-source-commit`. It builds that source with the pinned JDK and offline Gradle, archives its harness and staged classpath bytes, and runs each selected mode through the three API routes. Keep `TMPDIR`, `GRADLE_OPTS` for `java.io.tmpdir`, and the external key under the home directory. `verify` reads the archived inputs after the source checkout is removed; it does not need `--producer-root`.

```sh
TMPDIR="$HOME/dyn4k-performance-tmp" GRADLE_OPTS="-Djava.io.tmpdir=$HOME/dyn4k-performance-tmp" python3 tools/performance/sustained_host.py capture --archive "$HOME/dyn4k-v2-audit" --trusted-key "$HOME/keys/operator.key" --expected-source-commit EXACT_PRODUCER_SHA --producer-root /isolated/exact-source-checkout --java /path/to/jdk21/bin/java --javac /path/to/jdk21/bin/javac --baseline /path/to/pinned/dyn4j-6.0.0.jar --seconds 1 --warmup-seconds 1 --modes allocation,memory,plateau
python3 tools/performance/sustained_host.py verify --archive "$HOME/dyn4k-v2-audit" --trusted-key "$HOME/keys/operator.key" --expected-source-commit EXACT_PRODUCER_SHA
```

The signed version 2 result reports each selected mode as `executed_unqualified` with its verified route count. It never reports those executed paths as `NOT_RUN` or as a qualification pass. The verifier checks file hashes and complete sidecar inventory, exact source and staged inputs, loaded provider and fixture hashes, independent OS image and process interval, nonce, common clock origin, phase order, per-thread allocation counters, raw measured allocation, retained collection delta, and 100 ordered plateau cycles. The full signed verifier applies the same checks when these sidecars appear in a sustained part and copies them during merge. Its separate attributed-memory and plateau gates still reject null workload/native fields and legacy `-1` values. Increasing plateau collection counts establish collection events between observations; the version 2 stream lacks a before-collection count for each disposal, so it does not independently prove that every collection followed that cycle's disposal.

## Verification and current blockers

The verifier checks signed file hashes and recomputes summaries and intervals from raw streams. Public-entry synthetic controls exercised complete inventory, command, build, plateau, noise, exit, stress, timing, memory, and zero-allocation paths. The positive control used 2,000 seeded one-second paired-block draws. A 95% unchanged-baseline interval outside the approved noise range blocks candidate evaluation. The current manifest lacks that numeric range, so production verification stops with `unpassed policy`. A zero-allocation baseline accepts only zero candidate allocation. These controls test protocol behavior, not authentic reference hardware.

The current pilot and warm-up failures remain unpassed. The manifest still lists 0 of 28 validated reference environments. The versioned JVM harness emits allocation, memory, and plateau observations, but it does not establish workload/native/Wasm attribution or qualified retained-memory and plateau budgets. Non-JVM unchanged-baseline adapters and live validation of non-Linux process-image and stress probes remain absent. Approved harness binaries, noise admissibility, and sustained-stress ceilings remain delegated decisions. Synthetic controls, the bounded historical pilot audit, and the short versioned JVM host audit do not qualify hardware or a candidate artifact.

The trusted key authenticates the capture operator. It prevents an archive reader from changing hashes and re-signing a result. Semantic validation also rejects many wrong values after a trusted re-sign. The key holder and runtime adapter remain part of the trust boundary; an archive alone cannot prove that a dishonest operator ran real hardware.
