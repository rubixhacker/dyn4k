# Sustained performance raw archive

The [performance manifest task](https://github.com/rubixhacker/dyn4k/issues/17) remains open. The [version 1 manifest](../research/performance-manifest-v1.json) fixes the approved budgets and method. The public sustained verifier currently returns `qualification: unpassed`. The approved policy has no numeric admissible-noise or sustained-stress ceiling. It also has no approved harness, adapter, or A/A control artifact inventory. These decisions must be added to the frozen policy before production capture or verification. No reference row is qualified now. The historical `verify_candidate_archive.py` still audits the version 1 pilot and returns `unpassed`.

## Reference-study archive

The [bounded planning decision](https://github.com/rubixhacker/dyn4k/issues/17#issuecomment-6304248173) permits a separate reference study. `tools/performance/reference_study.py` creates, seals, and verifies its version 1 archive. Its result is `study: structurally_verified` with `qualification: unpassed`. It cannot supply a production noise limit, a stress ceiling, or a validated reference row. A structurally verified synthetic archive proves only the archive contract.

Use `create --archive DIR --plan PLAN.json --trusted-key KEY` before collecting study runs. The plan names source commit `bb7d5cf7671f96a13449a5e0c3d65ff44d4b4975`, a nonempty list of `{phase, key, controls}` assignments, and the controls used by those assignments. `phase` is `feasibility`, `source`, `model_holdout`, or `confirmation`. `key` is one exact comparison, row, scenario, mode, metric, and window key from the frozen 999-scenario, 21-target, 28-row manifest. The verifier checks the full manifest-derived key inventory and derives each key's required control IDs. The plan may declare a bounded subset; successful verification does not mean every manifest key was studied.

Each control supplies `row_id`, `control_id`, `route`, `host_id`, and `artifact_path`, `probe_path`, `runtime_path`, and `image_path`. The tool copies and hashes those files into the protocol archive. JVM versus dyn4j uses the `dyn4j_6_0_0_jvm` baseline route and requires the manifest's pinned dyn4j 6.0.0 JAR digest. Shim versus direct uses both `compatibility_self` and `direct_kotlin_self`. Absolute timing and memory use `row_reference_self`. These IDs fix the comparison assignment. Other study artifacts and hosts are recorded but not independently approved for qualification. The signed protocol binds its source commit, frozen manifest hash, complete key-inventory hash, tool source hash, control files, and assignments.

Use `seal --archive DIR --captures CAPTURES.json --trusted-key KEY` after collection. For each declared key and control, provide three process pairs with order `a,b`, `b,a`, `a,b`. Each capture names its phase, key, control, row, route, host, pair, side, order, unique process and run IDs, OS PID, monotonic process start and end, the four copied identity-file SHA-256 hashes, `series_path`, `environment_path`, `monitor_path`, `invalid_reason`, and `stop_reason`. The three raw files are copied and hashed. A complete study capture has `invalid_reason: null` and `stop_reason: completed`; another value stops structural verification. The verifier checks every declared pair slot and referenced byte, rejects extra fields and numeric limits, and rejects reused process or run IDs and raw hashes across source, model holdout, and confirmation phases. The trusted key must remain outside the archive.

Use `verify --archive DIR --trusted-key KEY --expected-source-commit bb7d5cf7671f96a13449a5e0c3d65ff44d4b4975` after moving an archive to an independent verifier. The signed protocol and archive index reject altered files, changed assignments, and a protocol edited after sealing. Keep the original protocol digest in an external study record before capture: a key holder can otherwise sign a replacement protocol before sealing. The current tool records claimed process, environment, and monitor identities but does not independently observe a future producer process or interpret the opaque raw series. A later reviewed producer must supply that evidence. A later independently reviewed calibration design must define statistical adequacy, phase separation, and any numeric noise or stress rule before those results can affect `sustained_archive.py`.

## Commands and archive boundary

Run one capture part on each validated reference host. Keep the trusted HMAC key outside every archive. The key must contain at least 32 bytes and must come from the independent gate operator. The same key verifies every part and the merged archive.

```sh
python3 tools/performance/sustained_archive.py plan
python3 tools/performance/sustained_archive.py init --archive HOST_PART --config REFERENCE_CONFIG.json --trusted-key TRUSTED_KEY
python3 tools/performance/sustained_archive.py capture --archive HOST_PART --job JOB.json --trusted-key TRUSTED_KEY
python3 tools/performance/sustained_archive.py merge --archive COMPLETE_ARCHIVE --part HOST_PART_1 --part HOST_PART_2 --trusted-key TRUSTED_KEY
python3 tools/performance/sustained_archive.py verify --archive COMPLETE_ARCHIVE --trusted-key TRUSTED_KEY --expected-source-commit EXACT_CANDIDATE_SHA
python3 tools/performance/sustained_archive.py verify-capacity --archive HOST_PART --trusted-key TRUSTED_KEY --expected-source-commit EXACT_CANDIDATE_SHA --capture-index SIGNED_REPORT_POSITION
```

Repeat `--part` for all 28 runtime rows after the pending policy decisions. `init` accepts one row and copies staged artifacts, independently approved control artifacts, the baseline JAR, runtime, harness, adapter, and probe samples. `capture` appends one signed process record. Failed and partial process files remain in the part and make full verification fail. `merge` checks signed parts, copies raw files, rejects duplicate rows, and applies the complete gate. A failed command exits nonzero and prints `qualification: unpassed` with a reason. The independent qualification adapter can call `verify` with its exact candidate SHA and inspect this JSON result. It must supply the trusted key through its own protected input outside the archive. `verify-capacity` checks one signed limit-stopped stress report in a host part. Its successful exit reports `capacity_limited` and keeps qualification, completed stress, small/medium pass, and release qualification false. A full `verify` rejects that report as sustained evidence.

The full plan has 999 frozen scenario IDs, 21 targets, and 28 runtime rows. It requires 113,886 small and medium process measurements, 18,981 stress reports, 111,888 A/A noise runs across timing, allocation, and memory modes, and 12,654 plateaus. These counts describe the complete protocol. They are not executed results. Stress is report only; small and medium retain the manifest's row-specific gate assignment.

## Reference config and job contract

The reference config has `source_commit`, `baseline_path`, `artifacts`, and `references`. `artifacts` maps one runtime row ID to absolute staged `core` and `kotlin` artifact paths. A non-JVM row also supplies `control_artifact_paths` with separately staged `core` and `kotlin` paths, plus `control_build_receipt_paths` for its independently approved optimized control. The control receipt names its source commit, artifact hashes, build configuration, target, and `built_from_frozen_control_source` status. `references` maps the same row ID to a validated environment record. The record must reproduce the row's target, runtime family, minimum policy, size assignment, development build, and optimized build. It must select the row's optimized build. It must include hardware, runtime version, ABI, host identity, support verification, and validated power, thermal, and load-window observations. The `runtime`, `harness`, and `adapter` records each need an absolute path. The runtime also needs a version. The `build_receipt.source_path` identifies a JSON receipt with exact source trees, both candidate artifact hashes, the optimized configuration, target, and `status: built_from_exact_source`. The probe needs `timer_source_path` for 10,000 positive `elapsed_ns` samples and `allocation_source_path` for a controlled allocation row. The payload must be at least 1 MiB, measured allocation must cover it, and collection count must be positive. Memory attribution must be validated for managed, native, and Wasm linear storage.

The pending `sustained_gate` policy section must name each row's approved harness and adapter SHA-256, fixture SHA-256, complete `command_prefix`, and exact `environment`. The JVM row must explicitly select `sidecar_protocol: jvm-v2` or an independently approved `legacy-v1` protocol. The current manifest selects neither. A `jvm-v2` selection requires the complete signed allocation, memory, and plateau sidecar inventory for every applicable JVM capture; a v1-only archive cannot pass that selection. The fixture hash covers the manifest's `fixture` and `joint_parameters` objects. Prefix tokens expand `{runtime}`, `{harness}`, `{adapter}`, `{baseline}`, `{core}`, and `{kotlin}` to selected absolute paths. The JVM prefix must include `-cp` and all five binary paths. The token array binds JVM flags, classpath, main class, and other settings. The producer passes only approved ambient variables plus its fixed `DYN4K_` output variables. The verifier rejects inserted command flags, environment options, and unapproved binary hashes. Loaded harness, adapter, fixture, and engine hashes must appear in the provider receipt.

The same frozen section must supply `noise_controls`, `comparison_controls`, and per-assignment `noise_upper_ratio_max`. Each assignment key names comparison, runtime row, candidate scenario ID, mode, metric, and full or final-minute window. The verifier requires the entire matrix. A missing, extra, or candidate-selected assignment fails before candidate analysis. The JVM control is the immutable dyn4j 6.0.0 artifact. Every non-JVM row needs a separately frozen same-target optimized port artifact; it measures host/runtime noise and is not the dyn4j performance baseline. Each control pins its source, artifact bytes, build, runtime image, harness, adapter, and probe. Non-JVM parts retain the control binaries and a policy-hashed exact-source build receipt. Noise captures run the frozen control in a fresh observed process. Timing, allocation, and retained-memory A/A streams use three balanced process pairs per workload and mode. The verifier completes all admissible-noise intervals before evaluating any candidate budget. It retains the prescribed 2,000 deterministic bootstrap draws with seed 17017 and checks full and final-minute windows where applicable.

The section also needs a `stress_limits` map with exactly the 28 frozen runtime row IDs. Each row record names its own `row_id`, `wall_stop_ns`, `wall_max_ns`, `rss_stop_bytes`, `rss_max_bytes`, and `rss_metric_kind`, plus SHA-256 digests of independently reviewed reference-overhead, monitor-validation, and host-capacity evidence. Missing, extra, or swapped row records fail policy validation. Both stop points must be below their row's hard bounds. The independent policy review must derive and approve each numeric record from that row's reference overhead, monitor error and units, and enforceable host capacity before adding it to the frozen policy. The verifier checks the frozen row map and its evidence identities; it does not derive a new numeric formula from candidate data. A verified stop may report measured overshoot within the approved row bounds. The [delegated policy keeps numeric calibration pending](https://github.com/rubixhacker/dyn4k/issues/17#issuecomment-6246347463). The checked-in manifest has no `sustained_gate`; the earlier 180-second and 3 GiB pilot limits do not approve sustained limits.

Each job identifies `kind`, `row_id`, `scenario_id`, `mode`, `repeat`, `sequence`, and an absolute `command` array. Noise jobs also identify `side` as `a` or `b`. Kinds are `measure`, `report`, `noise`, and `plateau`. Timing, allocation, and memory run in separate processes. Each gate measurement and noise run measures 600 paced seconds after 120 to 600 seconds of converged warm-up. Each gate measurement has three fresh process repeats. A completed stress report measures 60 seconds. A plateau has 100 create/use/dispose cycles after warm-up. The three measurement repeat orders are baseline/direct/compatibility, direct/compatibility/baseline, and compatibility/baseline/direct. Non-JVM measurement rows omit the JVM baseline process while retaining the selected candidate order. Noise jobs use baseline scenarios on JVM and direct-Kotlin scenarios with the separate control artifact on non-JVM rows. The control ID and source identity come from policy and producer records, not job input.

The command's trailing arguments are `family variant size hz steps mode warmup_steps` for the baseline. Candidate commands append `api`. The frozen scenario ID fixes every value. `capture` checks the entire command before launch. It records PID, monotonic start and end, observed host, binary hashes, and raw output hashes. It reads the executed image from Linux procfs, macOS libproc, or the Windows process API. The signed receipt binds the observed PID and monotonic time to the capture. Only the Linux probe has been exercised on this host. A wrapper must execute the measured runtime in the recorded process.

The runner writes the existing full step CSV to stdout and the full warm-up CSV to stderr. Its stderr must include the existing construction, RSS, and retained-heap markers and `#fixture_reset_after_warmup=1`. It should include `#process_pid` and `#route_marker` (`1` for direct Kotlin, `2` for compatibility). The producer sets these output paths in the runner environment:

| Variable | Required output |
| --- | --- |
| `DYN4K_PROVIDER_JSON` | API, process PID, expected source/artifact/baseline hashes echoed from the environment, and observed loaded code-origin hashes. The OS receipt independently identifies the runtime image. |
| `DYN4K_CLOCK_CSV` | `step,begin_ns,end_ns` for every measured step, using the same monotonic clock as elapsed time. |
| `DYN4K_WARMUP_CLOCK_CSV` | `warmup_step,begin_ns,end_ns` for every warm-up step, using the same monotonic clock. |
| `DYN4K_CLOCK_ORIGIN_JSON` | Runtime PID, monotonic origin stamp, and capture nonce, written by the same process before sampling. |
| `DYN4K_CLOCK_NONCE` | Fresh producer nonce copied into the origin record. |
| `DYN4K_MEMORY_CSV` | `phase,step,managed_bytes,native_bytes,wasm_linear_bytes,attributed_workload_bytes` for `empty`, `construction`, every warm-up step, and every measured memory step. |
| `DYN4K_RESOURCE_CSV` | Observed heap use, RSS, and allocation samples. These observations do not establish workload attribution. |
| `DYN4K_RUN_JSON` | Same-process sample count, measured wall time, activity count, resource peaks, and completion status. |
| `DYN4K_ALLOCATION_V2_JSONL` | Version 2 same-thread allocation counter pairs for construction, warm-up, measurement, or plateau cycles. |
| `DYN4K_MEMORY_V2_JSONL` | Version 2 heap, RSS, buffer-pool, and retained-collection observations. Workload and native attribution remain null. |
| `DYN4K_PLATEAU_V2_JSONL` | Version 2 ordered 100-cycle heap, RSS, and collection-count observations. Workload attribution remains null. |

The memory total must equal the sum of its three disjoint components. The empty workload reading is zero. The verifier checks the 16 MiB small and 64 MiB medium peak caps across construction, warm-up, and measurement. The process RSS stream remains diagnostic. A plateau writes 100 cycles with post-collection heap, RSS, collection count, managed, native, Wasm, total attributable, and reserved runtime bytes. Each attributable component and unexplained RSS residual must stay within the frozen 5% window drift rule. Reserved runtime bytes are recorded separately and require validated attribution.

The producer records the host monotonic interval from process launch to independent observation of the runtime's origin file. The signed origin receipt binds the runtime stamp, PID, and nonce to that interval and the observed process image. Both public verifiers require every warm-up and measured clock row to have positive duration and nonoverlapping monotonic order. One common feasible clock offset must place every row inside the observed process interval. A relative 600-second span alone does not establish that binding. The wide launch-to-origin bracket is deliberately retained in the receipt; a future host probe may narrow it. A trusted signer and runner remain part of the evidence boundary.

Stress runs write `elapsed_ns,rss_bytes,action` external monitor observations. Linux samples the observed PID's `VmHWM`, then obtains exact-child terminal `wait4` `ru_maxrss` in KiB and converts it to bytes. macOS samples `/bin/ps` for the exact PID during the run, converting its current RSS from 1024-byte units as specified by [Apple's `ps(1)` source](https://github.com/apple-oss-distributions/adv_cmds/blob/6bed8737a34dbb54782a18f47dccf933a9967a12/ps/ps.1). For terminal acceptance, macOS uses exact-child `wait4` `ru_maxrss` as bytes, following the [pinned XNU getrusage manual](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/man/man2/getrusage.2). [Apple's wait4 manual](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/wait4.2.html) documents the per-PID result. An older [Apple archived getrusage manual](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man2/getrusage.2.html) instead says kilobytes; the reference Mac's units remain to be validated. The verifier rejects a terminal value below any prior sample. `wait4` usage may include the child's own children, which makes that ceiling conservative if the runner spawns children. Windows samples [`PeakWorkingSetSize` in bytes](https://learn.microsoft.com/en-us/windows/win32/api/psapi/ns-psapi-process_memory_counters) and retains an OS process handle for a terminal `GetProcessMemoryInfo` query after wait. It binds that handle to the observed PID. The Windows policy metric is `peak_working_set_bytes`, distinct from POSIX `peak_rss_bytes`. If a terminal query fails, the report cannot be complete.

The signed monitor receipt binds the PID, process image, samples, terminal peak, observation time, exit code, and termination reason. A limit stop records its requested action and the times before and after successful OS dispatch. On Linux and macOS, `terminate` requires an exact-child SIGTERM wait status. `kill` requires SIGKILL. Exit code 1 or the opposite signal leaves capacity incomplete. On Windows, the producer calls native `TerminateProcess(..., 1)` on the original child handle after checking its PID. It records `stop_dispatch_method: windows_terminate_process_v1` and `stop_dispatch_result: os_success` only when that call returns success. [CPython 3.12.12](https://github.com/python/cpython/blob/v3.12.12/Lib/subprocess.py#L1667-L1682) can return normally from `Popen.terminate()` without making the native call when the child has already exited. A naturally exited child with code 1, an access-denied native call, or a missing dispatch result leaves capacity incomplete even if a terminal peak query succeeds. A successful native call, matching exit code 1, PID, handle, and terminal peak can support a complete capacity report. The signed receipt still depends on the trusted producer and key; the Windows native call and post-termination counter query need a hosted control on a reference Windows system.

The verifier checks the terminal peak against the row's hard bound. A transient spike after a live sample must appear in the terminal high-water record. A matched limit stop with complete hashed partial raw rows returns only `capacity_limited`. Missing terminal evidence, failed dispatch, mismatched POSIX signal, lost monitor, partial receipt, or hard-bound breach prevents completion. A zero-exit report that finishes all 60 seconds can be `completed`. It is not an absolute timing pass. Linux exact-child `wait4` is exercised on this host. Hosted Mac units and Windows post-termination counter availability remain reference-row validation work. [XNU's `ri_lifetime_max_phys_footprint`](https://github.com/apple-oss-distributions/xnu/blob/f6217f891ac0bb64f3d375211650a4c1ff8ca1ea/bsd/sys/resource.h) measures physical footprint. This route does not substitute that metric for RSS.

The provider JSON cannot attest the process image. The independent OS receipt supplies that digest. The provider's `loaded_core_sha256` must equal the pinned dyn4j JAR for baseline work or the staged core artifact for a candidate run. `loaded_kotlin_sha256` must equal the staged Kotlin artifact only for direct Kotlin. It is `null` on baseline and compatibility runs. `loaded_harness_sha256`, `loaded_adapter_sha256`, and `loaded_fixture_sha256` must match their approved policy values. These loaded hashes come from JVM code origins. The producer passes expected source, artifact, and baseline hashes in `DYN4K_SOURCE_COMMIT`, `DYN4K_ARTIFACT_HASHES_JSON`, and `DYN4K_BASELINE_SHA256`; the corresponding provider fields echo those environment values. Their equality is a consistency check, not independent proof of loaded bytes.

## Bounded JVM producer audit

The available host can run a short diagnostic against exact staged JVM artifacts. It executes baseline, direct Kotlin, and compatibility routes. It seals source trees, staged classpath bytes, commands, process-image receipts, and raw output with an external key. Its public verifier checks the raw streams and always returns `qualification: unpassed`.

```sh
python3 tools/performance/candidate_runner.py prepare /tmp/dyn4k-tools/jdk21/bin/java HEAD
python3 tools/performance/bounded_adapter.py capture --archive build/performance-bounded --trusted-key /path/outside/archive/operator.key --expected-source-commit EXACT_SOURCE_SHA --java /tmp/dyn4k-tools/jdk21/bin/java --javac /tmp/dyn4k-tools/jdk21/bin/javac --baseline /path/to/pinned/dyn4j-6.0.0.jar --seconds 1 --warmup-seconds 1
python3 tools/performance/bounded_adapter.py verify --archive build/performance-bounded --trusted-key /path/outside/archive/operator.key --expected-source-commit EXACT_SOURCE_SHA
```

Build and stage the exact source before `prepare`. The bounded route allows one to five seconds of warm-up and measurement. It records the three real JVM processes, OS image receipts, full step CSVs, warm-up CSVs, commands, and staged inputs. It reports missing sustained sidecars per route. The historical Java harness and direct Kotlin pilot do not emit in-process clock streams or fixture-reset markers. No available runner emits the full same-process provider and attributed memory records required by the sustained verifier. The bounded audit does not infer them from process RSS or command lines. Its successful exit means the retained bounded raw archive passed its diagnostic checks; it does not mean performance qualified.

## Versioned available-host JVM harness

`tools/performance/sustained_jvm/` contains separate Java and Kotlin adapters. They leave the historical `BaselinePilot.java` and its failed first pilot untouched. The adapters accept the manifest's family, variant, size, rate, step count, mode, and warm-up count. The Java baseline accepts the seven-argument production command; candidate calls append their API. They emit measured and warm-up clock streams, an explicit fixture-reset marker, a same-process provider receipt with SHA-256 of each loaded JAR origin, observed resource rows, and a run summary. The producer separately reads the executed OS process image and binds its digest to the PID and monotonic observation time. The loaded-JAR receipt corroborates JVM state; it is not an independent OS image receipt.

The public host producer builds exact-source staged JVM artifacts, compiles the separate harness, compiles the Kotlin adapter with `direct.init.gradle`, and executes all three API routes. It snapshots source, classpath, runtime, build receipt, commands, clock-origin receipts, and raw streams into a signed archive. Its verifier reads archived binary bytes after relocation, checks the external trusted key, recomputes input hashes, validates every clock row against one process-bound origin offset, checks resource agreement and run activity, and rejects re-signed changes. Use a home-backed `TMPDIR` and keep the key outside the archive:

```sh
TMPDIR="$HOME/dyn4k-performance-tmp" python3 tools/performance/sustained_host.py capture --archive "$HOME/dyn4k-sustained-host-audit" --trusted-key "$HOME/dyn4k-operator.key" --expected-source-commit EXACT_SOURCE_SHA --java /path/to/jdk21/bin/java --javac /path/to/jdk21/bin/javac --baseline /path/to/pinned/dyn4j-6.0.0.jar --seconds 1 --warmup-seconds 1
python3 tools/performance/sustained_host.py verify --archive "$HOME/dyn4k-sustained-host-audit" --trusted-key "$HOME/dyn4k-operator.key" --expected-source-commit EXACT_SOURCE_SHA
```

This host audit accepts only one to five seconds and labels its development build and memory attribution as unqualified. It is an integration proof for real processes and sidecars, not a 600-second calibration. Production `sustained_archive.py capture` passes the resource and run output paths to the same adapters and retains these streams when present. It still requires approved optimized build receipts, validated reference and probe records, attributed memory and plateau evidence, complete workload repeats, admissible noise, and stress ceilings. A short host archive is never accepted by the full gate.

The version 2 short archive accepts `--modes allocation,memory,plateau` and an optional `--producer-root` pointing to an isolated checkout at `--expected-source-commit`. It builds that source with the pinned JDK and offline Gradle, archives its harness and staged classpath bytes, and runs each selected mode through the three API routes. Keep `TMPDIR`, `GRADLE_OPTS` for `java.io.tmpdir`, and the external key under the home directory. `verify` reads the archived inputs after the source checkout is removed; it does not need `--producer-root`.

```sh
TMPDIR="$HOME/dyn4k-performance-tmp" GRADLE_OPTS="-Djava.io.tmpdir=$HOME/dyn4k-performance-tmp" python3 tools/performance/sustained_host.py capture --archive "$HOME/dyn4k-v2-audit" --trusted-key "$HOME/keys/operator.key" --expected-source-commit EXACT_PRODUCER_SHA --producer-root /isolated/exact-source-checkout --java /path/to/jdk21/bin/java --javac /path/to/jdk21/bin/javac --baseline /path/to/pinned/dyn4j-6.0.0.jar --seconds 1 --warmup-seconds 1 --modes allocation,memory,plateau
python3 tools/performance/sustained_host.py verify --archive "$HOME/dyn4k-v2-audit" --trusted-key "$HOME/keys/operator.key" --expected-source-commit EXACT_PRODUCER_SHA
```

The signed version 2 result reports each selected mode as `executed_unqualified` with its verified route count. It does not report those executed paths as `NOT_RUN` or as a qualification pass. The verifier checks signed files, exact source and staged inputs, loaded provider hashes, and the independent OS process image. It also checks nonce, common clock origin, phase order, allocation counters, raw measured allocation, and retained collection delta. Every warm-up memory observation must follow its step and precede the next step.

For each plateau cycle, the current version 2 contract records collection counts before and after a request. It stamps disposal, both count reads, the request, heap sampling, RSS sampling, and the final row. The verifier requires ordered stamps inside one observed process interval, a positive count delta for that cycle, and agreement with the legacy CSV. A later count increase cannot excuse one zero-delta cycle. The request stamp does not prove that the request caused collection or that the fixture was reclaimed. The earlier version 2 plateau rows lack these fields. Their archived bytes remain historical, but they do not satisfy the current plateau audit.

The full signed verifier applies the same sidecar checks to sustained parts and copies them during merge. If policy selects `jvm-v2`, it rejects absent or partial v2 streams for allocation, memory, and plateau captures. Valid v2 structure cannot pass a memory or plateau capture while workload, native, and reserved-runtime attribution remains null. A legacy memory CSV cannot substitute for that evidence. The complete synthetic legacy-v1 test uses an explicit test-only policy selector; it is not reference or production evidence.

## Verification and current blockers

The verifier checks signed file hashes and recomputes summaries and intervals from raw streams. Public-entry synthetic controls exercised complete inventory, frozen comparison maps, distinct non-JVM control bytes and build receipts, command, build, plateau, noise, exit, capacity stop, timing, memory, and zero-allocation paths. The full positive control used 2,000 seeded one-second paired-block draws. A 95% A/A interval outside its assigned noise range blocks all candidate budget analysis. Timing p99 and workload-memory assignments also cover absolute gates. The current manifest lacks approved numeric ranges, so production verification stops with `unpassed policy`. A zero-allocation baseline accepts only zero candidate allocation. These controls test protocol behavior, not authentic reference hardware.

The current pilot and warm-up failures remain unpassed. The manifest still lists 0 of 28 validated reference environments. Its independently pinned SHA-256 is `18cca97bbf1fc939eda669efe2344bbfe06c416a735ca8cc5184d5ba2519176a`. A future reviewed policy amendment must update that pin together with the generator and checked-in JSON; a candidate cannot supply an approval map through the archive or CLI. The versioned JVM harness emits allocation, memory, and plateau observations, but it does not establish workload/native/Wasm attribution or qualified retained-memory and plateau budgets. Independently frozen same-target non-JVM control artifacts and live validation of non-Linux process-image and stress probes remain absent. Approved harness binaries, noise admissibility, and sustained-stress limits remain delegated decisions. Synthetic controls, the bounded historical pilot audit, and the short versioned JVM host audit do not qualify hardware or a candidate artifact.

The trusted key authenticates the capture operator. It prevents an archive reader from changing hashes and re-signing a result. Semantic validation also rejects many wrong values after a trusted re-sign. The key holder and runtime adapter remain part of the trust boundary; an archive alone cannot prove that a dishonest operator ran real hardware.
