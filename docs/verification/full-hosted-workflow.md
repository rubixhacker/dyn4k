# Full hosted common corpus workflow

The hosted jobs run the reviewed common core and facade corpus against staged artifacts. Read `receipt.json` and the raw files together. A successful receipt establishes only the executed host, runtime, and configurations. It does not qualify every support lane.

## What runs

The native matrix covers macOS ARM64, iOS/tvOS/watchOS ARM64 simulators, iOS x64 simulator, and Windows x64. The Safari job covers JS in Safari. Each job first keeps the existing bounded probe and raw bundle. It then invokes `tools/qualification/full_hosted.py` and uploads the full evidence as a tar archive.

The runner requires the committed `full-common-corpus.json`, reviewed original map, and reviewed pair file. It regenerates the source inventory and rejects a changed source tree or unresolved mapping. The approved selection has 2,465 common core methods and 58 common facade methods. Each configuration must execute all 2,523 methods. The native jobs request both `debug-g` and `optimized-opt`. The Safari job requests both `development` and `production`. Inventory approval does not establish runtime qualification.

The runner checks the exact candidate head and tracked files with `qualify.require_clean_checkout`, whose generated-output allowance includes the external consumer. It then checks the corpus merger's committed manifest, map, and pair identities with `candidate_input_problems(check_checkout=False)`. This keeps consumer `.gradle` and `build` outputs from the earlier bounded probe out of the candidate source inventory.

The release native mode registers a release test binary through a temporary Gradle init script. It links the binary and points the test task at it. The simulator tasks use one recorded simulator UDID. The Safari mode selects Safari through an init script and uses the production JS test executable for its production run. Each configuration then runs an external portable consumer against the staged `dyn4k` and `dyn4k-core` target variants. That consumer has three bounded public cases. Its pass is evidence of artifact resolution; it is not a complete consumer compatibility corpus.

The runner removes old XML reports before each invocation. It checks exact common case IDs, XML counts, target suffixes, failures, skips, ignored cases, duplicates, and report times. It also resolves the external consumer's target compile dependency graph and records component IDs, resolved artifact paths, sizes, and SHA-256 values. Each target artifact must have the exact staged GAV and matching bytes. Gradle may report the staged file or its copy under the module cache. The graph task reports Gradle's effective user home separately from each artifact path. A cache path must be under that home, carry the exact GAV layout, and use the SHA-1 of the staged KLIB bytes as its digest directory. The verifier also compares Gradle's observation with the runner home or the recorded `GRADLE_USER_HOME` override. A relative override resolves against the recorded Gradle process cwd (`repository_root`). The `-p` project path does not change that cwd. The runner archives each resolved file and checks its bytes against the graph and staged binary hashes. The receipt records the GitHub run, runner, OS, selected simulator or Safari version, commands, process IDs, exits, timestamps, invocation IDs, case IDs, and hashes. It also records Java 21, Gradle 9.5.0, KGP 2.4.20, and AGP 9.3.1. A command failure or missing report gives `FAILED`. A missing simulator or Safari gives `UNAVAILABLE`; its full support lanes remain `NOT_RUN`. `FULL_COMMON_PASSED` means both local configuration checks completed; it is not the support matrix's `PASSED` status.

## Archive and independent verification

Gradle 9.5.0 may omit leading zeros from the staged KLIB's SHA-1 cache directory. The verifier accepts only that exact shortened spelling or the full 40-character digest at the recorded Gradle user home.

The separate full upload is a tar file containing `receipt.json` with schema 2 and an exhaustive `files` inventory. Every inventory entry has a safe relative path, byte size, modification time, and SHA-256. The tar also records the original nanosecond time for each member so downloading it cannot change report freshness evidence. The verifier rejects symlinks, duplicate or unsafe paths, missing files, and unlisted files. `inputs/` contains the reviewed manifest, map, pair file, foundation consumer manifest, source scanner, qualification scripts, and root and external consumer build files. `sources/` contains every reviewed test source file. `staged/` contains the root and target POM and Gradle metadata for both modules, plus target binaries and checksum sidecars. `dokka/` contains the producer's generated HTML for both modules. Its receipt provenance binds each file to the candidate and staging process. The verifier compares these archived pages with the documentation JARs. It does not read mutable Dokka output from the verifier's checkout. `stage/` and each configuration's `source/`, `consumer/`, and `graph/` contain raw stdout and stderr. Each configuration also contains raw source and consumer XML, test executable bytes, and every resolved dependency artifact, including transitive libraries. Its init scripts record the selected build mode and dependency graph task.

Archived Dokka pages establish internal evidence consistency and recorded process provenance. They do not cryptographically prove that Dokka generated those pages from the candidate source.

Run `python tools/qualification/full_hosted.py --verify-tar --candidate-sha <sha> --target <target> --archive <downloaded.tar>` against the exact candidate checkout. The verifier safely extracts the tar into a temporary directory and restores original member times from its recorded headers. It reloads the committed inventory, requires both configurations and common modules, reparses XML, and compares every executed ID to the reviewed manifest. It checks the pinned toolchain fields and the original time of each process log against its invocation window. It verifies the consumer's three expected IDs, process exits, task output, resolved graph, artifact bytes, executables, staging metadata, paths, and timestamps. A synthetic `<testsuite tests='1'/>` with no testcase, a missing configuration, or a consumer result without its resolved graph fails. The workflow verifies both the local directory and the tar before upload. Upload on failure preserves diagnostic bytes but does not create a pass.

## Record and qualification status

Run `artifact.py verify --full-hosted` against the directory or downloaded tar from a clean checkout at the receipt's exact candidate SHA. This public ingress uses the same exhaustive verifier as `full_hosted.py`. It checks the staged publication, archived Dokka pages, transport timestamps, source cases, consumer cases, and resolved artifacts.

```bash
python3 tools/qualification/artifact.py verify --candidate-sha <sha> --output <downloaded.tar> --full-hosted
python3 tools/qualification/qualify.py record --candidate-sha <sha> --full-hosted-bundle <downloaded.tar> --output <qualification.json>
```

The record command maps a verified receipt to the selected current configuration lanes. Inspect `full_hosted_receipts` in `qualification.json` even when the command exits 1. That exit means the complete 112-lane matrix remains unpassed. The committed `full-suite-manifest.json` controls all selected cases and additional gates. A `FULL_COMMON_PASSED` receipt does not supply absent compatibility, consumer, independent, or release evidence.

Use the observed runtime and configuration for each recorded lane. A current observation cannot establish a minimum-OS pass. Windows Server 2025 does not establish a Windows 10 client pass. A simulator cannot establish a physical-device pass. Run the hosted workflow and remaining gates at the final assembled SHA before claiming qualification. Unavailable runtimes and missing independent evidence remain `NOT_RUN` or `UNPASSED`.
