# Full hosted common corpus workflow

The hosted jobs run the reviewed common core and facade corpus against staged artifacts. Read `receipt.json` and the raw files together. A successful receipt establishes only the executed host, runtime, and configurations. It does not qualify every support lane.

## What runs

The native matrix covers macOS ARM64, iOS/tvOS/watchOS ARM64 simulators, iOS x64 simulator, and Windows x64. The Safari job covers JS in Safari. Each job first keeps the existing bounded probe and raw bundle. It then invokes `tools/qualification/full_hosted.py` and uploads the full evidence as a tar archive.

The runner requires the committed `full-common-corpus.json`, reviewed original map, and reviewed pair file from the corpus merger. It regenerates the source inventory and rejects a changed source tree or unresolved mapping. The source count is 2,465 common core methods, including six collision diagnostics and five rotation observation isolation methods, and 58 common facade methods. This manifest successor awaits independent approval. Each configuration must execute all 2,523 methods. The native jobs request both `debug-g` and `optimized-opt`. The Safari job requests both `development` and `production`.

The runner checks the exact candidate head and tracked files with `qualify.require_clean_checkout`, whose generated-output allowance includes the external consumer. It then checks the corpus merger's committed manifest, map, and pair identities with `candidate_input_problems(check_checkout=False)`. This keeps consumer `.gradle` and `build` outputs from the earlier bounded probe out of the candidate source inventory.

The release native mode registers a release test binary through a temporary Gradle init script. It links the binary and points the test task at it. The simulator tasks use one recorded simulator UDID. The Safari mode selects Safari through an init script and uses the production JS test executable for its production run. Each configuration then runs an external portable consumer against the staged `dyn4k` and `dyn4k-core` target variants. That consumer has three bounded public cases. Its pass is evidence of artifact resolution; it is not a complete consumer compatibility corpus.

The runner removes old XML reports before each invocation. It checks exact common case IDs, XML counts, target suffixes, failures, skips, ignored cases, duplicates, and report times. It also resolves the external consumer's target compile dependency graph and records component IDs, resolved artifact paths, sizes, and SHA-256 values. The two staged target binaries must appear at their staging paths with matching hashes. The receipt records the GitHub run, runner, OS, selected simulator or Safari version, commands, process IDs, exits, timestamps, invocation IDs, case IDs, and hashes. It also records Java 21, Gradle 9.5.0, KGP 2.4.20, and AGP 9.3.1. A command failure or missing report gives `FAILED`. A missing simulator or Safari gives `UNAVAILABLE`; its full support lanes remain `NOT_RUN`. `FULL_COMMON_PASSED` means both local configuration checks completed; it is not the support matrix's `PASSED` status.

## Archive and independent verification

The separate full upload is a tar file containing `receipt.json` with schema 2 and an exhaustive `files` inventory. Every inventory entry has a safe relative path, byte size, modification time, and SHA-256. The tar also records the original nanosecond time for each member so downloading it cannot change report freshness evidence. The verifier rejects symlinks, duplicate or unsafe paths, missing files, and unlisted files. `inputs/` contains the reviewed manifest, map, pair file, foundation consumer manifest, source scanner, qualification scripts, and root and external consumer build files. `sources/` contains every reviewed test source file. `staged/` contains the root and target POM and Gradle metadata for both modules, plus target binaries and checksum sidecars. `stage/` and each configuration's `source/`, `consumer/`, and `graph/` contain raw stdout and stderr. Each configuration also contains raw source and consumer XML, test executable bytes, and every resolved dependency artifact, including transitive libraries. Its init scripts record the selected build mode and dependency graph task.

Run `python tools/qualification/full_hosted.py --verify-tar --candidate-sha <sha> --target <target> --archive <downloaded.tar>` against the exact candidate checkout. The verifier safely extracts the tar into a temporary directory and restores original member times from its recorded headers. It reloads the committed inventory, requires both configurations and common modules, reparses XML, and compares every executed ID to the reviewed manifest. It checks the pinned toolchain fields and the original time of each process log against its invocation window. It verifies the consumer's three expected IDs, process exits, task output, resolved graph, artifact bytes, executables, staging metadata, paths, and timestamps. A synthetic `<testsuite tests='1'/>` with no testcase, a missing configuration, or a consumer result without its resolved graph fails. The workflow verifies both the local directory and the tar before upload. Upload on failure preserves diagnostic bytes but does not create a pass.

## Integration handoff

The current `qualify.py record` and `artifact.py` accept the bounded hosted probe. Their complete-lane API expects a different `complete-port` suite manifest, candidate lane selection, and staged audit. The corpus merger owns the reviewed common manifest, so this branch leaves those files untouched. After the merger lands, adapt the qualification ingress as follows:

1. Add a full hosted bundle input to `qualify.py record`. Accept only schema 2 `hosted-full-common-corpus` receipts with `FULL_COMMON_PASSED` after `full_hosted.verify_raw_files` succeeds against the exact candidate checkout. The receipt's `configurations` array must equal `debug-g, optimized-opt` for native or `development, production` for Safari. Each entry has `source_process`, `consumer_process`, `graph_process`, `source`, `consumer`, `consumer_graph`, `resolved_artifacts`, `source_executables`, and `consumer_executable`; top-level `files`, `staged_gav`, `artifact_hashes`, `stage`, `runtime`, and source hashes bind the archive. Do not consume the status string alone.
2. Map the source-derived common IDs into the complete suite's area and lane schema. Preserve its JVM-only and platform-only exclusions. Require every additional compatibility and consumer case specified by that suite; the 2,512 common methods alone cannot satisfy a complete lane.
3. Bind each actual runtime version, configuration, simulator UDID or Safari version, candidate SHA, and both staged binary hashes to the candidate manifest and artifact audit. Do not assign a hosted pass to the `minimum` version by copying a `current` observation. Do not assume Windows Server 2025 is the approved Windows 10 client runtime.
4. Extend `artifact.py verify` to call `full_hosted.verify_transport_archive(tar_path, candidate_sha, target)` and bind its result to the candidate's 112 exact matrix IDs. Keep bounded bundle verification independent. A failed full verification, an incomplete configuration, and every unavailable hosted runtime remain `NOT_RUN` in the complete matrix.

The reviewed corpus commit is merged into this isolated branch. The coordinator must still run the workflow at the approved assembled SHA after integration. This branch cannot execute GitHub Actions without a push. Until an exact-head hosted run and full-lane ingestion pass, all 112 lanes remain unpassed. Physical Apple devices, minimum OS versions, and other unavailable targets require their own execution.
