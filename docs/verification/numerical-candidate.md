# Candidate numerical capture on staged JVM artifacts

This page describes the candidate recorder for [Run the full compatibility corpus and unchanged migration applications](https://github.com/rubixhacker/dyn4k/issues/42). The exact commit, artifact hashes, commands, and observed trace hashes are in `/tmp/dyn4k-candidate-numerical-result.md`. Candidate numerical acceptance is open.

## Consumer and receipt

`tools/numerical/candidate/` is a Java consumer of the staged `io.github.rubixhacker:dyn4k-core-jvm:0.1.0-alpha.1` artifact. Its Gradle runtime graph check requires that artifact and rejects `org.dyn4j:dyn4j`. Each scene constructs `org.dyn4j.world.World` from the assembled common Kotlin engine. The scene sources adapt the pinned calibration and sleep/wake input recipes. The separate Weld/Pulley physical capture uses the declared physical input. No baseline Java runtime provides the captured world.

The frozen catalog in `tools/numerical/fixtures.json` still controls the 14 accepted trace members. `run.py` requires a clean commit and a staged JAR. It runs one consumer, validates the trace with the approved record parser, seals a receipt, and runs `compare.py` against the matching frozen timestep and member. A trace with extra or missing callbacks has no valid receipt. The raw trace and `run.log` remain available to diagnose failure. The receipt records the Git commit, SHA-256 of `git archive --format=tar HEAD`, staged JAR hash, trace and frozen reference hashes, exact expected and executed counts, runtime, host, and candidate build configuration hash. The recorder process writes `runtime.json` with its JVM version, executable, process ID and start time, and loaded engine code source. `receipt.py` checks the loaded engine bytes against the staged JAR and binds the executable and runtime stamp hashes. Its verification recomputes these identities and rejects stale, missing, or extra fields.

The Java recorder writes `Double.toString` numeric tokens. This preserves `-0.0`. The parser retains its sign and `compare.same_value` checks exact aliases by binary64 bits. A signed zero can compare numerically as zero under an approved numeric rule while still failing an exact same-run alias if its paired getter changes sign. Endpoint records copy the current inner state. They do not call `World.step`, advance event order, or add simulated time.

Use a fresh output path for each run. For example:

```sh
./gradlew --no-daemon :dyn4k-core:publishJvmPublicationToStagingRepository :dyn4k:publishJvmPublicationToStagingRepository
PYTHONDONTWRITEBYTECODE=1 python3 tools/numerical/candidate/run.py --fixture default-sleep-30 --reference /path/to/S-sleep-wake-hz30-0.jsonl.gz --output /tmp/candidate-default-30
PYTHONDONTWRITEBYTECODE=1 python3 tools/numerical/candidate/receipt.py verify --fixture default-sleep-30 --trace /tmp/candidate-default-30/S-sleep-wake-hz30-0.jsonl.gz --receipt /tmp/candidate-default-30/receipt.json
```

`same_run.py` checks candidate body getter and transform aliases, fixed-body callback velocities, instrumented snapshots, and endpoint copies. It reports a local alias result. The complete approved six-group exact-consistency package still needs a candidate-path execution before a full same-run claim. `sleep_physical.py` reuses the frozen represented-geometry phase definitions and ceilings. An unsealed trace can be measured with `--diagnostic`, which labels the result unbound. A receipt-bound pass requires `--receipt`. The declared Weld/Pulley physical checker uses the frozen declaration and the same exact-rational geometric metrics as the baseline audit.

## Isolated host matrix

`matrix.py` compiles the same Java calibration sources separately against the staged candidate and pinned baseline JAR. It uses an explicit Java 21 compiler and executable. The candidate process loads no baseline JAR. Its eight batches cover 585 geometry queries; 30 motion, 195 contact, 232 joint-mode, 92 joint-checkpoint, 25 joint-interaction, 180 CCD, and 91 long-run cases. Motion, contact, CCD, and long-run batches split by the 15 declared scale/origin pairs and run at most four recorder processes concurrently. Each process retains its own runtime stamp and case files. Checkpoint preparation rows and the Pulley preparation rows are retained in addition to those case counts. The calibration recorder records a failed mode in `summary.jsonl`, closes its partial gzip trace, executes later modes, and exits nonzero after the matrix. The failed Angle ratio -1 case therefore remains failed even when subsequent Distance through Wheel modes execute.

The first filter term must match the start of a case ID; later terms select the scale, origin, or timestep. `FilterProbe` checks this against the staged consumer. In particular, `L-` must not select a CCD case merely because its mode contains `ALL-`. Every selected long-run case has the declared 600-second duration.

The runner writes compressed traces and a streaming-hash manifest under a new output directory on the home disk. It records each case's input-line hash, decompressed and gzip hashes, record counts, failure step or setup exception, loaded provider hash, source archive hash, build configuration, and the executing JVM command and binary hash. Pair diagnostics identify missing cases, count differences, input differences, and byte differences. They do not grant numerical parity to new calibration cases without approved limits. `WorldQualityProbe` separately executes Java 8-source controls on actual Java 8 and 21 processes against each provider. It is a short World smoke, not a Java 8 frozen-schema recorder. The calibration Java source requires Java 21.

`ccd_control.py` runs the root's SHA-pinned creation-index body-hash diagnostic against the pinned baseline and coherent staged candidate. Its four offsets are separate prospective inputs. The control retains all previous CCD traces and leaves the engine's `HashMap` ordering intact. A matching result diagnoses order sensitivity; it does not replace a frozen CCD reference or qualify the full corpus.

The Java 21 recorder compiled with `javac --release 21`; its default 30/60/120 Hz and configured 30 Hz gzip hashes equal the Java 25 captures. The recorder's Java source uses Java 9+ factories and Java 16+ language features, so `javac --release 8` rejects it. A separate Java 8-compatible staged `WorldQualityConsumer` compiled with `--release 8` produced six default/configured 30/60/120 Hz rows identical on Temurin 8 and 21. That smoke run is not a frozen-schema Java 8 capture. Common Kotlin portable capture and frozen comparability require their own executed target evidence.

## Observed gates

The default candidate records have frozen event and state counts and pass local getter aliases. Their represented-geometry diagnostic fails at 17,999/18,000 (30 Hz), 35,996/36,000 (60 Hz), and 71,852/72,000 (120 Hz): 125,847/126,000 combined. The frozen baseline has the same failed total. It remains a physical failure.

All six configured candidate traces have 72,000 inner states and the specified 18,000, 36,000, or 72,000 copied endpoints. Each has 935,991 events against 935,967 frozen events. The first extra contact callbacks occur at inner step 36,001 after the approved wake impulse. Each configured trace passes the local alias check and has zero diagnostic penetration failures. Their event mismatch prevents a valid comparator receipt or parity claim; the physical measurements remain unbound diagnostics.

An independent pinned-baseline capture reproduces the approved configured gzip. A mixed diagnostic using the actual Kotlin Vector2 and simplex repairs then reproduces all runtime rows of all six configured members exactly, including 935,967 events per member. Its sole differing row is the input header: `ConservativeAdvancement.getDistanceEpsilon` is `4.806217383937355e-6` from `pow(1/3)` instead of the baseline `4.806217383937352e-6` from `Math.cbrt`. The detection source owner owns that default. These mixed artifacts are diagnostic and do not satisfy a coherent candidate receipt or exact input identity.

The nominal free-motion candidate has 36,000 states, 108,001 events, 600 simulated seconds, and zero observed energy and momentum drift in the capture summary. A separate capture compiled against only the pinned baseline JAR reproduces the frozen nominal gzip, decompressed stream, and input hashes exactly. The old candidate runtime rows then match that member exactly, while its input header retains the TOI epsilon difference. This baseline-only reconstruction supplies a local frozen reference; it is not candidate parity or a current receipt.

The old Weld member and both Pulley preparation members match frozen record counts. The old Pulley transition has 3,600 events against 3,730 frozen events; the first structural divergence is at step 332, order 7. Its physical residual acceptance remains unpassed, including the earlier slack-enabled 0.1208278904872957 m extension and 39 samples above the diagnostic 0.005 m solver tolerance.

The current default and old Weld runtime records match their frozen members after the input header. Pulley preparation 1 and the old transition additionally differ in numerical records. In a separately labelled mixed diagnostic containing the actual Kotlin Vector2 and simplex repairs, the old Pulley transition recovers all 3,730 events and its numeric runtime fields match the frozen trace. The remaining difference was the compiler-generated class name of the public `ManifoldPointId.DISTANCE` singleton. The recorder now serializes that one object by identity to the frozen `ManifoldPointId$1` protocol tag, as it already does for `Filter.DEFAULT_FILTER`; all other IDs keep their runtime class names. `ProtocolTagProbe` passes on the staged candidate and pinned baseline JAR and rejects relabelling a custom lookalike ID. A fresh baseline-only Pulley run with the adapter reproduces all three approved gzip hashes byte for byte. With the adapter, the mixed diagnostic's every runtime row for all three Pulley members matches the frozen traces. The input header still differs, and the mixed artifact is not accepted coherent candidate parity.

The separate prospectively declared Weld spring/equal-limit and taut Pulley candidate captures each executed 36,000 steps and 108,000 ordered callbacks. On the staged JVM, the represented Weld anchor maximum was 0.0010240181055693979 m and its angle maximum was 0.0014456701862869353 rad. The taut Pulley maximum absolute rope error was 0.0041245829551926905 m. Both are below their respective declared 0.01 m and one-degree limits. These new physical checks do not repair the old four-member physical gap or the default sleep/wake failure.

The fixed numerical limits, full same-run package, complete fixture matrix, target runtime math paths, unchanged migration applications, and all required native/device lanes remain separate open gates. The configured sine norm and formula-specific comparison assume finite normal binary64 inputs, round-to-nearest arithmetic, the selected operation envelope, and target `sin`, `cos`, and `acos` behavior. A JVM result does not prove those premises on JS, Wasm, native, Android, or Apple runtimes.
