# Candidate numerical capture on staged JVM artifacts

This page describes the candidate recorder for [Run the full compatibility corpus and unchanged migration applications](https://github.com/rubixhacker/dyn4k/issues/42). The exact commit, artifact hashes, commands, and observed trace hashes are in `/tmp/dyn4k-java-numerical-valid-distance-exact-result.md`. Candidate numerical acceptance is open.

## Consumer and receipt

`tools/numerical/candidate/` is a Java consumer of the staged `io.github.rubixhacker:dyn4k-core-jvm:0.1.0-alpha.1` artifact. Its Gradle runtime graph check requires that artifact and rejects `org.dyn4j:dyn4j`. Each scene constructs `org.dyn4j.world.World` from the assembled common Kotlin engine. The scene sources adapt the pinned calibration and sleep/wake input recipes. The separate Weld/Pulley physical capture uses the declared physical input. No baseline Java runtime provides the captured world.

The frozen catalog in `tools/numerical/fixtures.json` still controls the 14 accepted trace members. `run.py` requires a clean commit and a staged JAR. It runs one consumer, validates the trace with the approved record parser, seals a receipt, and compares the matching frozen timestep and member. Default members use the owned `default_policy.py` overlay; configured members retain their approved catalog rules. A trace with extra or missing callbacks has no valid receipt. The raw trace and `run.log` remain available to diagnose failure. The receipt records the Git commit, SHA-256 of `git archive --format=tar HEAD`, staged JAR hash, trace and frozen reference hashes, exact expected and executed counts, runtime, host, and candidate build configuration hash. The recorder process writes `runtime.json` with its JVM version, executable, process ID and start time, and loaded engine code source. `receipt.py` checks the loaded engine bytes against the staged JAR and binds the executable and runtime stamp hashes. Its verification recomputes these identities and rejects stale, missing, or extra fields.

The Java recorder writes `Double.toString` numeric tokens. This preserves `-0.0`, and the parser retains its sign for receipt and nominal positive-zero checks. The dedicated six-group same-run checker compares finite numeric alias and endpoint values, so `+0.0` equals `-0.0`; object key order does not matter. This follows the [corrected acceptance decision](https://github.com/rubixhacker/dyn4k/issues/7#issuecomment-6243770998). Endpoint records copy the current inner state. They do not call `World.step`, advance event order, or add simulated time.

Use a fresh output path for each run. For example:

```sh
./gradlew --no-daemon :dyn4k-core:publishJvmPublicationToStagingRepository :dyn4k:publishJvmPublicationToStagingRepository
PYTHONDONTWRITEBYTECODE=1 python3 tools/numerical/candidate/run.py --fixture default-sleep-30 --reference /path/to/S-sleep-wake-hz30-0.jsonl.gz --output /tmp/candidate-default-30
PYTHONDONTWRITEBYTECODE=1 python3 tools/numerical/candidate/receipt.py verify --fixture default-sleep-30 --trace /tmp/candidate-default-30/S-sleep-wake-hz30-0.jsonl.gz --receipt /tmp/candidate-default-30/receipt.json
```

Run the full same-run audit on each captured default or configured member. Supply the source commit that produced the loaded JAR. Use a new identity path for `seal`:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 tools/numerical/candidate/exact_consistency.py seal --fixture configured-30-r1 --trace /path/to/Q-sleep-wake-outer30-repeat1-0.jsonl.gz --artifact /path/to/dyn4k-core-jvm.jar --source-commit SOURCE_SHA --identity /path/to/exact-identity.json
PYTHONDONTWRITEBYTECODE=1 python3 tools/numerical/candidate/exact_consistency.py verify --fixture configured-30-r1 --trace /path/to/Q-sleep-wake-outer30-repeat1-0.jsonl.gz --artifact /path/to/dyn4k-core-jvm.jar --source-commit SOURCE_SHA --identity /path/to/exact-identity.json
```

`same_run.py` is an `UNBOUND_DIAGNOSTIC` local alias check. It checks state and endpoint indices and copies, but skips input records and cannot establish frozen input identity. `sleep_physical.py --diagnostic` is likewise unbound. Candidate qualification requires receipt verification, and the dedicated `exact_consistency.py` six-group audit checks the frozen input hash directly. The central `compare.check_counts(..., reference=False)` is an internal receipt count check, not an independent input-identity verdict. `exact_consistency.py` audits the six approved same-run groups on default and configured sleep/wake streams: fixed floor and callback velocity, zero applied force, sleeping velocity and pose, immediate center impulse, getter aliases with phase-correct previous copies and ten duplicate getters, and timestep metadata. It requires the frozen input hash, strict schemas and counts, ordered callbacks, and the approved configured method counts. Endpoint copies are checked immediately after their inner state and never become the temporal prior. Its candidate identity file binds the gzip and decompressed hashes, World source archive and JAR, recorder Java sources and compiled classes, Java executable, and recorder-process runtime stamp. `seal` creates an identity file; `verify` recomputes it. `reference` checks frozen input, gzip, and decompressed hashes. The full six-group result remains specific to its source and JVM artifact.

`run.py` enforces positive binary64 zero in each post-step nominal `force`, `torque`, `accumulatedForce`, and `accumulatedTorque` field on both reference and candidate before calling the approved comparator. The owned check rejects negative zero, integer zero tokens, nonfinite values, missing fields, and nonzero values without changing the frozen fixture or central comparator. The delegated [fixed nominal timestep policy](https://github.com/rubixhacker/dyn4k/issues/7#issuecomment-6243538631) also requires five exact finite binary64 getters at every nominal `StepListener` callback, including `updatePerformed`. The [correction](https://github.com/rubixhacker/dyn4k/issues/7#issuecomment-6243770998) makes these exact numeric values independent of JSON spelling: decoded `60` and `60.0` are equal, while bool, string, nonfinite and wrong values fail. Record indices still require integer schema. The candidate consumer checks the values independently on both streams, records 540,005 checks per provider, and selects exactly these five numeric paths in its local comparator overlay. `sleep_physical.py` reuses the frozen represented-geometry phase definitions and ceilings. An unsealed trace can be measured with `--diagnostic`, which labels the result unbound. A receipt-bound pass requires `--receipt`. The declared Weld/Pulley physical checker uses the frozen declaration and the same exact-rational geometric metrics as the baseline audit.

The [delegated default policy](https://github.com/rubixhacker/dyn4k/issues/7#issuecomment-6243730891) selects all 137 required numeric path templates in `default_paths.json`: 50 exact identities, 12 numeric zeros, 61 fields under the unchanged configured budgets, and 14 source-derived values. The candidate overlay copies those rule shapes from the frozen configured profile without changing that profile or the default references. Its inventory audit requires each path in the frozen baseline and rejects any unclassified candidate field. It checks five exact finite binary64 timestep values on both providers at every callback, with the initial 60 Hz previous step and the selected 30/60/120 Hz current step. A separate source-math audit checks the rotation setting, operation envelope, stored coefficient norm, cosine/angle relation, sine sign, and recorder scope for each provider before applying the stored trigonometric formulas. Failed premises leave the affected coefficient paths `UNPASSED`; a broken six-group consistency rule independently fails the case. The result records each required path's verdict and recomputes the source archive, loaded JAR, recorder source and class set, executable, runtime stamp, trace, and build configuration identities from the actual process.

## Isolated host matrix

`matrix.py` compiles the same Java calibration sources separately against the staged candidate and pinned baseline JAR. It uses an explicit Java 21 compiler and executable. The candidate process loads no baseline JAR. Its eight batches cover 585 geometry queries; 30 motion, 195 contact, 233 joint-mode, 92 joint-checkpoint, 25 joint-interaction, 180 CCD, and 91 long-run cases. Motion, contact, CCD, and long-run batches split by the 15 declared scale/origin pairs and run at most four recorder processes concurrently. Each process retains its own runtime stamp and case files. Checkpoint preparation rows and the Pulley preparation rows are retained in addition to those case counts. The calibration recorder records a failed mode in `summary.jsonl`, closes its partial gzip trace, executes later modes, and exits nonzero after the matrix. The failed Angle ratio -1 case therefore remains failed even when subsequent Distance through Wheel modes execute.

The first filter term must match the start of a case ID; later terms select the scale, origin, or timestep. `FilterProbe` checks this against the staged consumer. In particular, `L-` must not select a CCD case merely because its mode contains `ALL-`. Every selected long-run case has the declared 600-second duration.

The runner writes compressed traces and a streaming-hash manifest under a new output directory on the home disk. It records each case's input-line hash, decompressed and gzip hashes, record counts, failure step or setup exception, loaded provider hash, source archive hash, build configuration, and the executing JVM command and binary hash. Pair diagnostics identify missing cases, count differences, input differences, and byte differences. They do not grant numerical parity to new calibration cases without approved limits. `WorldQualityProbe` separately executes Java 8-source controls on actual Java 8 and 21 processes against each provider. It is a short World smoke, not a Java 8 frozen-schema recorder. The calibration Java source requires Java 21.

`ccd_control.py` runs the root's SHA-pinned creation-index body-hash diagnostic against the pinned baseline and coherent staged candidate. Its four offsets are separate prospective inputs. The control retains all previous CCD traces and leaves the engine's `HashMap` ordering intact. A matching result diagnoses order sensitivity; it does not replace a frozen CCD reference or qualify the full corpus.

The Java 21 recorder compiled with `javac --release 21`; its default 30/60/120 Hz and configured 30 Hz gzip hashes equal the Java 25 captures. The recorder's Java source uses Java 9+ factories and Java 16+ language features, so `javac --release 8` rejects it. A separate Java 8-compatible staged `WorldQualityConsumer` compiled with `--release 8` produced six default/configured 30/60/120 Hz rows identical on Temurin 8 and 21. That smoke run is not a frozen-schema Java 8 capture. Common Kotlin portable capture and frozen comparability require their own executed target evidence.
