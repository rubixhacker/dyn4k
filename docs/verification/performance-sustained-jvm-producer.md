# JVM memory and plateau producer contract

The JVM adapters emit version 2 JSONL when the runner supplies `DYN4K_ALLOCATION_V2_JSONL`, `DYN4K_MEMORY_V2_JSONL`, and `DYN4K_PLATEAU_V2_JSONL`. Each line carries schema 2, PID, capture nonce, source commit, SHA-256 of the same-process provider JSON, frozen fixture SHA-256, API route, family, variant, size, rate, mode, monotonic nanoseconds, and byte units. The independent runner must retain these files and bind their hashes to its process and image receipts. A producer line alone does not authenticate the runtime or qualify a reference row.

The allocation stream records the current thread ID, cumulative `ThreadMXBean.getThreadAllocatedBytes` before and after each construction, warm-up, measured step, or plateau create/use cycle. The adapter requires the probe for allocation, memory, and plateau modes. It enables a disabled probe when possible. Unsupported probes and negative or regressing readings terminate the process. The timed step CSV still records the step delta, so a verifier can cross-check the two streams.

The memory stream records same-process heap use and its delta from the empty harness. It also records JVM direct and mapped buffer-pool use as a process observation. A retained sample with the measured fixture alive records a positive observed collection-count delta and `managed_post_collection=true`. If the delta is zero, the producer closes the partial sidecars and exits without a retained row. These observations do not identify all objects reachable from the fixture and do not allocate native runtime memory to the workload. `native_workload_bytes` and `attributed_workload_bytes` are `null`; `native_attribution` is `unsupported`; qualification is `unpassed`. A verifier must not convert these values to zero or accept the heap delta as a validated attributable component.

Plateau mode writes the same-process `DYN4K_WARMUP_CLOCK_CSV` for every paced warm-up step, then runs 100 create/use/dispose cycles. Each cycle creates the same family, variant, and size, runs two simulated seconds with the fixture's mutation schedule, returns from the fixture method, requests collection, and records heap use, RSS, buffer-pool use, and per-thread cycle allocation. Every version 2 plateau row carries `cycle_disposed_ns`, `collection_before_sample_ns`, `gc_requested_ns`, `collection_after_sample_ns`, `collection_count_before`, `collection_count_after`, `collection_count_delta`, `collection_count_unit=collections`, `collection_probe`, and `collection_count_status=observed`. These monotonic time anchors and counters bind a positive observed collection delta to the interval after that cycle's fixture method returned; the GC request alone is not proof. The legacy `collection_count` equals `collection_count_after`. If any collector count is unknown, or if the cycle has no new collection, the producer closes partial sidecars and exits without that cycle's plateau row. A verifier must require a positive delta on each of exactly 100 rows and check the anchors in order. The existing plateau CSV includes `-1` for unvalidated managed, native, total, and reserved-runtime attribution. The version 2 stream uses `null` for the unvalidated components. The collection evidence does not establish workload attribution or a memory-cap pass.

The focused JDK 21 controls are in `tools/performance/test_sustained_jvm_memory.py` and `test_sustained_jvm_p2_candidate.py`. They run one-step memory processes and 100-cycle plateaus against the pinned baseline and staged candidate JVM artifacts. They reject missing or fabricated allocation samples, a wrong provider digest, missing or implausible cycles, unsupported and negative allocation probes, and zero observed collection under `-XX:+DisableExplicitGC` on Java and direct Kotlin. They also check the plateau warm-up clock against stderr elapsed time and the same-process origin. These are producer protocol controls. The [performance manifest task](https://github.com/rubixhacker/dyn4k/issues/17) still needs a validated workload attribution method, approved probe and harness inventory, reference runs, and full sustained integration before qualification can pass.
