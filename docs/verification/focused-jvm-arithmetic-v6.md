# Focused JVM arithmetic receipt

## What the command checks

The version 6 receipt covers one Boolean method and one case: captureRevoluteLimitsFalse and joint-Revolute-LimitsEnabled-false. It keeps the approved 600 steps, 1,800 observed pivot calls, 1,200 body-step receipts, three caller locations, and fixed input and reference bytes.

The capture retains raw timestamped worker and helper traces. The verifier checks protected operations before it projects syntax for the older process readers. It keeps the original bytes and hashes. The selected worker must read the response and rebuilt agent inputs, write the direct mirror, and produce the class-load, argument, and class witness files at their recorded destinations.

The focused Gradle process passes the pinned Linux JDK's `FORK` process launch option through `JAVA_TOOL_OPTIONS`. The selected worker's effective startup record must contain the option once. Its fork child may close inherited descriptors, map four pipes, inspect `/proc/self/fd`, and set close-on-exec before its first Java execution. Replay checks that narrow sequence and rejects pre-Java reads, writes, sockets, child creation, other file opens, and protected paths. The `/proc/self/fd` descriptor must remain open through its stat call and close once. The raw transport reader also recognizes the historical pinned `jspawnhelper` prelude for bounded standalone checks. The helper process still has one selected Java execution.

Replay joins the traced Gradle invocation to its Java wrapper, the daemon process, and the selected worker through supported thread-sharing and process-birth records. The wrapper must launch its JAR with `-jar`. The daemon name must be the Java main class, followed by the pinned Gradle version. A matching name in JVM options, classpath, or application arguments is not a daemon main. The selected worker must likewise be the Java main. A thread-shaped clone cannot stand in for a new process. Replay checks that the wrapper and daemon images remain established through the selected child birth, including other traced threads of those processes. It uses each clone entry as the causal birth boundary, so the child may run before the parent clone returns.

When a raw worker or helper trace exposes the synthetic environment marker or forbidden key name, capture rejects it before creating an eligible receipt. It moves the rejected trace into a separate private directory beside the requested archive. That directory has mode 0700, its files have mode 0600, and its bytes count toward the unchanged capture budget. Its `UNVERIFIED` marker means those bytes are for private diagnosis only. They are never replay evidence.

The focused capture now builds the child environment from pinned tool paths, locale, derived user identity and Gradle cache path, plus the validated private temporary path. It preserves `HOME` and `CODEX_HOME` exactly, including empty or absent values. It does not copy caller option, proxy, or credential variables. The same policy reaches Gradle, the JDI helper compiler, the class witness compiler, and the version 6 receipt rebuilds. The exact synthetic canary remains present. Gradle may transfer its safe value between the client and daemon. Capture and public version 6 replay reject the forbidden key name and the full canary pair in raw or decoded strace strings. This check is bounded to trace strings; it is not a decoder for the full Gradle protocol. Rejected bytes remain private diagnostics.

Version 6 checks each protected descriptor use across threads, copies, reassignment, and closure. For helper outputs, it permits sequential writes, close, fstat, and an initial zero-length ftruncate before any write. It rejects operations that can change the file offset or bytes outside the byte reader's model. Its helper output scope includes every archived JDI file. The byte check reads the projected trace only after the raw destination check succeeds.

The strict transport check reads the raw worker and helper traces before normalization. It rejects completed split syscalls because normalization represents them at resume time and cannot prove their entry time. The narrow terminal abandoned accept exception remains subject to the raw lifecycle check. This version 6 limit does not change the older receipt behavior.

Version 6 uses a fixed reader profile for each raw worker or helper ZIP. The ZIP bytes and declared and actual decoded totals must each be at most 268,435,456 bytes. The ZIP may have at most 1,024 members and 2,000,000 physical lines across those members. A physical line is one newline-terminated raw record, including its newline bytes. Each record may contain at most 1,048,576 bytes. The reader checks member names, duplicates, links, decoded sizes, line counts, and record lengths before it projects a trace or credits JDI transport. It reads records with a bounded line buffer and verifies each member's CRC. The older raw and projected readers retain their 134,217,728-byte limits. The separate complete-process ZIP reader and the capture budget keep their own existing limits.

The first unchanged 600-step capture at source `184f2b23` produced 167,124,627 decoded worker bytes and 186,055,559 decoded helper bytes. Both exceeded the older 128 MiB raw-reader bound, so no version 6 receipt was admitted. The measured line totals were 1,075,001 and 1,539,856. The fixed version 6 profile covers these observed resource sizes, subject to all existing semantic and privacy checks. It does not admit that old archive or change numerical acceptance. A fresh reviewed-source capture remains necessary.

The verifier checks the raw accept, the live worker listener, the helper peer, and both sides of the JDWP handshake. It uses each handshake thread's file order to establish that end's handshake. Later packets may run on other proved threads of the selected process and shared descriptor table. Every event in a child trace must occur at or after each successful clone entry in its ancestor chain. A child event may share the clone entry timestamp because the reported creation edge supplies causal order; the parent need not return from clone first. The next syscall entry on the handshake thread proves that its handshake syscall returned. A packet on another thread must enter strictly after that entry. Packets on the handshake thread use its file order. If the trace has no such completion witness, it cannot credit a packet from another thread. A strace line timestamp records syscall entry, so the verifier does not treat timestamps from different processes as completion order.

The successful socket calls, exact peer tokens and handshake bytes, and live descriptor scope establish the selected exchange. It checks the selected socket lifetime through every credited exchange event. The raw lifetime check recognizes decorated and undecorated first descriptor operands. It treats descriptor 5 and descriptor 50 as different values. While a selected socket is live, version 6 rejects copied descriptor tables, socket descriptor aliases, and unsupported table changes. This narrow scope also rejects a copied child that only closes its own socket descriptor. The older socket and file status values remain unpassed records; they do not establish this version 6 transport proof.

The bounded JDI pilot writes the worker and helper raw trace archives and a diagnostic marked `UNVERIFIED` before proof checks. A failed pilot retains those bytes for diagnosis. A separate passing pilot summary records the completed checks; the raw diagnostic alone is not proof.

The source-CI loader toy uses its selected JDK 21 for Java execution, helper compilation, and its strict transport check. The test scopes that JDK identity to the toy verifier call and restores the production pin afterward. Focused capture and public replay still require the pinned production runtime. The published `02e9d287` source run failed at this test configuration boundary; a corrected test needs renewed source review and exact-main CI.

The capture records each rebuilt helper class file's identity before and after execution. Replay checks the selected helper process's complete reads of every class file it accessed. The main helper class must be read. The helper's effective startup log and the worker's effective startup log must contain only their permitted agent options. Both logs are tied to the selected process and their raw file writes.

The class witness records each relevant definition, successful load, provider, and loader label. At the unique Transform class-prepare event, JDI reads the agent's retained loader object, label, and definition ordinal. The verifier compares JVM object IDs with JVM object IDs. It joins the local label and ordinal to the terminal witness record. It also compares the loaded Transform and agent helper code with their source-derived bytes.

The direct mirror must equal the complete XML output in order, including its final newline. The existing caller, receiver, thread, order, bit, signed-zero, and arithmetic-oracle checks still apply. A passing focused receipt is method evidence with outer qualification UNPASSED. It does not change the fixed 32-ulp result or activate the conditional budget.

Version 6 binds the direct mirror before it selects a projected operation writer. The separate output wrapper keeps the original mirror FileChannel open through a status observation after the last write. The raw proof checks that observation on the original FD, all successful writes, and the final close. For the three argument and class-load logs, it checks the original initial device and inode, the permitted initial zero-end seek and truncate, all writes, and final close. It rejects aliases, replacement and unsupported offset changes. The older transport reader remains unchanged.

After the complete Gradle and helper process graphs exit, one traced read-only observer checks the four output objects in a fixed role order. The observer runs a fixed source literal through the measured capture interpreter. Replay checks its executable bytes, argument list, declared controlled environment, trace inventory, ordered no-follow opens, status calls, closes and zero exit. Each observed device and inode must match the original writer object; each final size must match the complete raw writes and archived bytes. The observer raw ZIP is part of the exact receipt and privacy scan. A rejected observer trace remains in the private UNVERIFIED directory and counts toward the existing budget.

The observer also checks protected operands before interpreter exec. Unprotected launch calls may precede exec. Protected input or output work in that prefix rejects, including calls recorded at the same timestamp as exec.

The observer checks every structural descriptor decoration, including non-leading arguments, nested control operands and returned descriptors. It checks pathname arguments only in syscall positions that name a file. Quoted buffer text cannot identify an operand. The shared raw validator checks known protected descriptors when a required decoration is missing. Child creation, descriptor duplication, close ranges and message-based descriptor transfer reject throughout the trace. Between each protected open and its close, only that descriptor's single identity stat and close are accepted. Unprotected interpreter startup reads and maps outside those four intervals remain supported.

Every other operation-marked write stream remains visible. Version 6 requires complete XML-ordered marker copies and an independent live local socket object with all writes and a final close across proved shared-table threads. This is a local output classification. It does not identify the remote peer or the application protocol. Unknown or partial marked channels reject. Versions 3 through 5 retain their single marked stream rule. The JDWP socket and handshake proof stays separate.

The socket proof credits complete writes from every proved shared-table writer on the selected live object, including writers whose own stream has no operation marker. It compares every such raw write with the same thread and descriptor in the checked projected ZIP. It rejects missing or changed projected writes and markers split across writes. The legacy writer check still requires each marked stream to contain the complete ordered XML marker lines. Other output calls on the live socket, including vector writes, sends and file-to-socket transfers, reject. The proof checks output operands without treating FD digits or path text in quoted payloads as operands.

## Capture and replay

Capture requires a clean committed source tree, the pinned JDK 21, the existing staged build tools, and a private home-backed TMPDIR whose path is at most 40 bytes. The output directory must be new and outside the source tree. The indexed reference case must have the pinned bytes.

The initial and final source checks use an explicit focused mode. Their Git children receive the same controlled environment as the focused capture. An omitted source-check mode fails before Git starts. Older capture profiles select their legacy mode explicitly.

Run the capture with:

~~~text
python -B tools/numerical/portable/capture_actual.py --method captureRevoluteLimitsFalse --output ABSOLUTE_NEW_ARCHIVE --reference-case ABSOLUTE_INDEXED_REFERENCE
~~~

Replay with an independently sealed JVM lane, its baseline archive, and its external baseline attestation:

~~~text
python -B tools/numerical/portable/capture_actual.py --verify-existing ABSOLUTE_ARCHIVE --lane ABSOLUTE_SEALED_JVM_LANE --baseline ABSOLUTE_BASELINE --attestation ABSOLUTE_ATTESTATION
~~~

Replay first runs the existing whole-lane comparison with no arithmetic-capture override. It then recomputes the version 6 receipt from raw files and compares the focused case bytes with the validated lane case. A Boolean-only archive root remains insufficient for the 15-method arithmetic verifier.

The external baseline attestation binds the exact bytes of `baseline_capture.py`, `run.py`, `cases.py`, and `receipt.py`. The published `80808b11` source changed `run.py` while adding focused Git environment selection. Its four-file digest differs from the retained attestation, so it cannot pass that source prerequisite. The corrected source restores the attested `run.py` bytes. The focused receipt instead uses the focused clean-source check and compares the full Git archive through the controlled child environment. This source compatibility check does not verify the baseline archive or qualify the focused method.
